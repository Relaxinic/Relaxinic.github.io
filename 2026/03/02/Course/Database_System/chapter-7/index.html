1 Introduction

1.1 Decomposition

Decompose a schema containing redundant information into several smaller schemas without redundancy.

Lossy decomposition: The resulting schemas from decomposition are non-redundant, but the schema obtained by naturally joining them back together contains more redundancy. Lossless decomposition: The opposite.

1.2 Normalization Theory

Methodology for avoiding duplicate information issues when designing relational databases.

2 Functional Dependencies

2.1 Keys and Functional Dependencies

functional dependencies: a set of constraints used to identify uniquely specific attribute values in a relation

For a relation schema r(R)r(R)r(R) and its attributes α,β⊆R\alpha, \beta \subseteq Rα,β⊆R

  • For an instance of r(R)r(R)r(R), if for all its tuple pairs t1,t2t_1, t_2t1​,t2​, when t1[α]=t2[α]t_1[\alpha] = t_2[\alpha]t1​[α]=t2​[α], it holds that t1[β]=t2[β]t_1[\beta] = t_2[\beta]t1​[β]=t2​[β], then the instance is said to satisfy the functional dependency α→β\alpha \rightarrow \betaα→β

  • If all instances of r(R)r(R)r(R) satisfy the functional dependency α→β\alpha \rightarrow \betaα→β, then the dependency is said to hold on r(R)r(R)r(R)

Therefore, there may be instances that satisfy some functional dependencies that do not hold over the entire relation schema

Redefine superkey using the concept of functional dependency: K→RK \rightarrow RK→R holds on r(R)r(R)r(R)

For a functional dependency α→β\alpha \rightarrow \betaα→β, if β⊆α\beta \subseteq \alphaβ⊆α, then this functional dependency is trivial.

Closure: the complete set of all functional dependencies derived from the functional dependency set F.

Now we define lossless decomposition using functional dependencies: when R1∩R2→R1/R2R_1 \cap R_2 \rightarrow R_1 / R_2R1​∩R2​→R1​/R2​ is satisfied, R1,R2R_1,R_2R1​,R2​ form a lossless decomposition of RRR.

3 Normal Forms

3.1 Boyce-Codd Normal Form

Regarding the relation RRR with the set of functional dependencies FFF, for all functional dependencies α→β\alpha \rightarrow \betaα→β in F+F^+F+, where α⊆R,β⊆R\alpha \subseteq R, \beta \subseteq Rα⊆R,β⊆R, RRR is said to be in BCNF if at least one of the following conditions holds:

  • α→β\alpha \rightarrow \betaα→β is a trivial functional dependency

  • α\alphaα is a superkey for schema RRR

In simple terms, as long as a functional dependency is "non-trivial," its left-hand side must be a superkey.

For schemas that do not comply with BCNF, we need to decompose them into:

  • (α∪β)(\alpha \cup \beta)(α∪β), placing the "determining factor" and the "determined attribute" together

  • (R−(β−α))(R - (\beta - \alpha))(R−(β−α)), remove the redundancy from the original relationship

Continue decomposing until all results adhere to BCNF.

Dependency Preservation: Suppose a relation RRR has a set of functional dependencies FFF. After decomposition, we obtain subrelations R1,R2,…RnR_1, R_2, \dots R_nR1​,R2​,…Rn​ with corresponding sets of functional dependencies F1,F2,…FnF_1, F_2, \dots F_nF1​,F2​,…Fn​. If (F1∪F2∪⋯∪Fn)+=F+(F_1 \cup F_2 \cup \dots \cup F_n)^+ = F^+(F1​∪F2​∪⋯∪Fn​)+=F+, then the decomposition is said to be dependency preserving.

Decompositions that follow the BCNF schema are not necessarily dependency preserving.

3.2 Third Normal Form

Regarding a relation RRR with a set of functional dependencies FFF, for all functional dependencies α→β\alpha \rightarrow \betaα→β in F+F^+F+, where α⊆R,β⊆R\alpha \subseteq R, \beta \subseteq Rα⊆R,β⊆R, RRR is said to be in the third normal form (3NF) if at least one of the following conditions is satisfied:

  • α→β\alpha \rightarrow \betaα→β is a trivial functional dependency

  • α\alphaα is a superkey for schema RRR

  • Each attribute AAA in β−α\beta - \alphaβ−α is a member of a (possibly different) candidate key of RRR

The third condition allows non-trivial functional dependencies whose left-hand side is not a superkey to still conform to this normal form. This more relaxed condition enables 3NF to ensure that the original dependencies are preserved during schema decomposition.

The drawback is that it may introduce null values, indicating the presence of information redundancy.

If BCNF and dependency preservation cannot be satisfied simultaneously, prioritize BCNF.

3.3 More Normal Forms

  • 4NF: Will be discussed below

  • 5NF: Based on a generalized multi-valued dependency—join dependencies, also known as project-join normal form (PJNF). The drawback of this normal form is not only that it is difficult to reason about, but also that its inference rules lack soundness and completeness.

  • 2NF: Its issues can be resolved by 3NF.

  • 1NF: Will be discussed below.

3.4 Atomic Domains and First Normal Form

First Normal Form: In a relational schema RRR, all attribute domains must be atomic (i.e., indivisible into smaller units).

Issues arising from non-atomicity include: complex storage, redundant data, and complicated queries.

  • For composite attributes: Use their component attributes directly.

  • For multivalued attributes: Multiple fields / a separate table / a single field.

4 Functional-Dependency Theory

4.1 Closure of Functional Dependencies

logically implied: For a given relation schema r(R)r(R)r(R), if every instance that satisfies the set of functional dependencies FFF also satisfies the functional dependency fff, then it is said that fff on RRR is logically implied by FFF.

Armstrong's axioms:

  • Reflexivity rule: If α\alphaα is a set of attributes, and β⊆α\beta \subseteq \alphaβ⊆α, then α→β\alpha \rightarrow \betaα→β holds.

  • Augmentation rule: If α→β\alpha \rightarrow \betaα→β holds, and γ\gammaγ is a set of attributes, then γα→γβ\gamma \alpha \rightarrow \gamma \betaγα→γβ holds.

  • Transitivity rule: If both α→β\alpha \rightarrow \betaα→β and β→γ\beta \rightarrow \gammaβ→γ hold, then α→γ\alpha \rightarrow \gammaα→γ holds.

Additional rules derived from the above rules：

  • Union rule: If α→β\alpha \rightarrow \betaα→β and α→γ\alpha \rightarrow \gammaα→γ hold, then α→βγ\alpha \rightarrow \beta\gammaα→βγ holds.

  • Decomposition rule: If α→βγ\alpha \rightarrow \beta\gammaα→βγ holds, then α→β\alpha \rightarrow \betaα→β and α→γ\alpha \rightarrow \gammaα→γ hold.

  • Pseudotransitivity rule: If α→β\alpha \rightarrow \betaα→β and γβ→δ\gamma\beta \rightarrow \deltaγβ→δ hold, then αγ→δ\alpha\gamma \rightarrow \deltaαγ→δ holds.

4.2 Closure of Attribute Sets

For attribute BBB and a set of attributes α\alphaα, if α→B\alpha \rightarrow Bα→B holds, then BBB is functionally determined by α\alphaα.

To check whether α\alphaα is a superkey, compute the closure α+\alpha^+α+ (i.e., the attribute closure) of α\alphaα, which includes all attributes that can be functionally determined by α\alphaα under a set of functional dependencies FFF.

This algorithm has the following uses:

  • Testing whether α\alphaα is a superkey: Compute α+\alpha^+α+, and check whether it contains all attributes of RRR.

  • Testing whether a functional dependency holds: To check whether α→β\alpha \rightarrow \betaα→β is valid, verify whether β⊆α+\beta \subseteq \alpha^+β⊆α+.

  • An alternative way to compute F+F^+F+: For all γ⊆R\gamma \subseteq Rγ⊆R, compute its closure γ+\gamma^+γ+. Then, for all S⊆γ+S \subseteq \gamma^+S⊆γ+, derive the functional dependency γ→S\gamma \rightarrow Sγ→S.

4.3 Canonical Cover

Extraneous attributes: attributes that, when removed, do not alter the closure of functional dependencies.

  • Removing attributes from the left side of a functional dependency will form a stronger constraint that exists.
  • Removing attributes from the right side of a functional dependency will form a weaker constraint that exists.

canonical cover FcF_cFc​

  • All dependencies that can logically imply FFF

  • The functional dependencies do not contain redundant attributes

  • The left-hand side of the functional dependencies is unique

4.4 Dependency Preservation

Let FFF be a set of functional dependencies on a schema RRR, and let R1,R2,…,RnR_1, R_2, \dots, R_nR1​,R2​,…,Rn​ be a decomposition of RRR.

For each RiR_iRi​, the restriction of FFF to RiR_iRi​, denoted as FiF_iFi​, is a set of functional dependencies derived from F+F^+F+, but containing only attributes that appear in RiR_iRi​.

Checking these restricted sets F1,F2,…,FnF_1, F_2, \dots, F_nF1​,F2​,…,Fn​ is more efficient than checking the original set FFF.

Let F′=F1∪F2∪⋯∪FnF' = F_1 \cup F_2 \cup \dots \cup F_nF′=F1​∪F2​∪⋯∪Fn​. In general, F′≠FF' \ne FF′=F. However, it is still possible that F′+=F+F'^+ = F^+F′+=F+. In this case, every dependency in FFF is logically implied by F′F'F′.

Therefore, verifying F′F'F′ is equivalent to verifying FFF. A decomposition with this property is called a dependency-preserving decomposition.

Three methods for verifying dependency preservation:

  • Compute F+F^+F+, which is computationally expensive.

  • If every member in FFF can be found in one of the decomposed subrelations, then the decomposition is dependency-preserving. This method is only a sufficient condition.

  • For each dependency α→β\alpha \rightarrow \betaα→β in FFF, perform the following: Starting from α, repeatedly "extend the inferable attributes" across the subtables to see if β can eventually be covered.

5 Algorithms for Decomposition Using Functional Dependencies

5.1 BCNF Decomposition

A relation satisfies BCNF if and only if for every nontrivial functional dependency α→β\alpha \rightarrow \betaα→β, its left-hand side α\alphaα is a superkey.

To avoid the high complexity of computing F+F^+F+, it can be determined by computing the attribute closure α+\alpha^+α+: if α+\alpha^+α+ contains all attributes of the relation RRR, then it satisfies BCNF.

For decomposed subrelations RiR_iRi​, relying solely on FFF is no longer sufficient. It is necessary to compute α+\alpha^+α+ for each attribute subset α⊆Ri\alpha \subseteq R_iα⊆Ri​.

If there exists an α+\alpha^+α+ that implies new attributes within RiR_iRi​ that are not all attributes, then the corresponding dependency α→(α+−α)∩Ri\alpha \rightarrow (\alpha^+ - \alpha)\cap R_iα→(α+−α)∩Ri​ violates BCNF.

5.2 3NF Decomposition

  • Create a table for each dependency

  • If none of the tables contain a candidate key, add another table that includes the candidate key to ensure lossless join

  • Remove duplicate or included tables to eliminate redundant structures

6.1 Multivalued Dependencies

Function dependencies are sometimes called equality-generating dependencies, while multi-valued dependencies are called tuple-generating dependencies.

The formal definition of multi-valued dependency: let r(R)r(R)r(R) be a relation schema, α⊆R\alpha \subseteq Rα⊆R and β⊆R\beta \subseteq Rβ⊆R. That is to say, it must satisfy the Cartesian product.

If the relation RRR satisfies α↠β\alpha \twoheadrightarrow \betaα↠β for all instances, then α↠β\alpha \twoheadrightarrow \betaα↠β is a trivial multivalued dependency on RRR.

The uses of multivalued dependencies include:

  • Checking whether a relation is legal under a given set of functional and multivalued dependencies

  • Specifying constraints on the set of legal relations, so that we only need to consider relations that satisfy the given functional and multivalued dependencies

Let DDD be a set of functional and multivalued dependencies. Its closure D+D^+D+ is the set of all functional and multivalued dependencies logically implied by DDD, which can be computed from the definitions of functional and multivalued dependencies.

  • If α→β\alpha \rightarrow \betaα→β, then α↠β\alpha \twoheadrightarrow \betaα↠β, meaning that all functional dependencies are multivalued dependencies.

That is to say, when β\betaβ has only one value under α\alphaα, the free combination condition automatically holds.

  • If α↠β\alpha \twoheadrightarrow \betaα↠β, then α↠R−α−β\alpha \twoheadrightarrow R - \alpha - \betaα↠R−α−β (symmetry).

6.2 Fourth Normal Form

Regarding a relation RRR with a set of functional and multivalued dependencies DDD, for every multivalued dependency α↠β\alpha \twoheadrightarrow \betaα↠β in D+D^+D+, where α⊆R,β⊆R\alpha \subseteq R, \beta \subseteq Rα⊆R,β⊆R, RRR is said to be in fourth normal form (4NF) if at least one of the following conditions holds:

  • α↠β\alpha \twoheadrightarrow \betaα↠β is a trivial multivalued dependency

  • α\alphaα is a superkey for RRR

Let R1,R2,…,RnR_1, R_2, \dots, R_nR1​,R2​,…,Rn​ be a decomposition of RRR. To check whether each relation schema RiR_iRi​ is in 4NF, we need to find the multivalued dependencies that hold on RiR_iRi​.

For a set DDD of functional and multivalued dependencies, the restriction DiD_iDi​ of DDD to RiR_iRi​ consists of:

  • All functional dependencies in D+D^+D+ that involve only attributes of RiR_iRi​;

  • All multivalued dependencies of the form α↠β∩Ri\alpha \twoheadrightarrow \beta \cap R_iα↠β∩Ri​, where α⊆Ri\alpha \subseteq R_iα⊆Ri​ and α↠β\alpha \twoheadrightarrow \betaα↠β is in D+D^+D+.

7 Database-Design Process

7.1 E-R Model and Normalization

  • There are functional dependencies among attributes within an entity set.

  • For relationship sets involving more than two entity sets, the relational schema obtained through conversion may not adhere to the required normal forms.

During the E-R design process, we can utilize known functional dependencies to identify these potential poor designs and perform normalization.

In E-R design, there is a tendency to generate designs that comply with 4NF. If multivalued dependencies are valid and are not implied by corresponding functional dependencies, they typically originate from many-to-many relationship sets or multivalued attributes of entity sets.

7.2 Naming of Attributes and Relationship

An ideal characteristic of database design: the unique-role assumption, meaning that each attribute name has only one meaning in the database.

7.3 Denormalization for Performance

In some applications, redundancy leads to performance improvements, and database designers actually prefer having redundant information.

The process of denormalizing normalized data is called denormalization.
