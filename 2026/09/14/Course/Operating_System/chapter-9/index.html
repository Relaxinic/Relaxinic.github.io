This chapter will introduce various methods for managing memory, each with its own advantages and disadvantages. Multiple factors need to be considered when choosing these methods, especially the hardware design of the system, because most algorithms require hardware support.

1 Background

Logically, memory consists of a very large array of bytes, with each byte having a corresponding address. As for a memory unit, it can only see a stream of memory addresses and does not know how they are generated (and we do not care about this either), or what purpose they serve (instruction/data).

The following discussion will cover several issues related to managing memory: basic hardware, the binding of virtual addresses and physical addresses, and the differences between the two.

1.1 Basic Hardware

The main memory and registers built into the processing unit are the only general-purpose storage devices that the CPU can directly access. Generally speaking, accessing a register requires only one CPU clock cycle, but completing a memory access requires multiple CPU clock cycles. For the latter, the processor usually stalls because the execution of subsequent instructions requires the memory data. However, we cannot tolerate such stalls because this would severely damage performance. The solution is to insert a cache between the CPU and memory to achieve faster access.

In addition to speed, another issue of concern is ensuring the correctness of operations. This needs to be achieved through protection provided by the hardware, because the OS usually cannot intervene between the CPU and its memory accesses. Specifically, the first thing to do is to ensure that each process has a separate memory space. This can be achieved through the base register and the limit register, which respectively store the smallest valid physical memory address and the size of the memory space.

Any attempt by a program executing in user mode to access OS memory or other users' memory (that is, access beyond the area delimited by the base register and the limit register) will trigger an OS trap and be treated as a fatal error, thereby protecting memory.

The base register and the limit register can only be loaded by the OS, and privileged instructions are required. Thus, the OS in kernel mode can access OS memory and user memory without restriction.

1.2 Address Binding

Addresses in a source program are usually symbolic. The compiler generally binds these symbolic addresses to relocatable addresses, and then the linker or loader binds the relocatable addresses to absolute addresses.

The operation of binding instructions and data to memory addresses can be accomplished in any one of the following ways:

Compile time: If it is known at compile time that the process will be in memory, then absolute code is generated; if the starting address of the process changes later, the code must be recompiled.

Load time: If it is not known at compile time whether the process will be in memory, then the compiler must generate relocatable code, and the final binding is deferred until load time; if the starting address of the process changes later, the code only needs to be reloaded to incorporate this new changed value.

Execution time: If the process can move within memory segments during execution, then binding must be deferred until run time (most OSs use this method).

1.3 Logical v.s. Physical Address Space

The addresses generated by the CPU are usually logical addresses; the address visible to a memory unit, that is, the address loaded into the memory-address register, is a physical address.

If addresses are bound at compile time and load time, then the logical address = the physical address; if addresses are bound at execution time, then the two are different.

In the latter case, the logical address is generally called a virtual address.

All logical addresses generated by a program are called the logical address space; correspondingly, there is also the concept of the physical address space.

The runtime mapping from virtual addresses to physical addresses is performed by a hardware device called the memory-management unit (MMU).

At this time, the base register is called the relocation register, and its value R is added to every address sent to memory when the user process generates an address; assuming the virtual address range is [0, max], then the corresponding physical address range is [R, R + max].

Therefore, a user program will never access a real physical address; it can manipulate only virtual addresses.

1.4 Dynamic Loading

Currently, the size of a process is limited by physical memory. To achieve higher memory space utilization, dynamic loading can be used. With this technique, routines are loaded only when they are called; all routines are stored on disk in a relocatable load format.

The advantage of this technique is that routines can be loaded only when needed, which is very useful for situations that require a large amount of code to handle infrequently occurring cases (such as handling errors), because although the program is large, only a small portion is loaded. In addition, this technique does not require special support from the OS, although some library functions may be provided to support dynamic loading.

1.5 Dynamic Linking and Shared Libraries

Dynamic linking libraries (DLLs) are system libraries that are linked to user programs at runtime. With dynamic linking, the linking process is deferred until execution time, thereby reducing the size of the executable image. In addition, DLLs can be shared by multiple processes, so only one instance of a DLL is needed in main memory.

The concept of DLLs can also be extended to library updates—when a new version of a library is adopted, all programs that reference that library automatically use the new version (without dynamic linking, manual relinking would be required).

Unlike dynamic loading, dynamic linking requires help from the OS.

Some OSs support only static linking, in which case system libraries are treated as ordinary object modules and are combined by the loader into a binary program image. In this case, each program contains a copy of the library in its executable image, which not only increases size but also wastes memory.

2 Contiguous Memory Allocation

Memory is usually divided into two parts: one part is allocated to the OS, and the other part is allocated to user processes. In most OSes, the memory allocated to the OS is generally at high addresses.

In contiguous memory allocation, each process is contained in a separate memory section, and that section is contiguous with the section containing the next process.

2.2 Memory Allocation

The simplest memory allocation scheme is the variable-partition scheme:

Assign variable memory partitions to processes, with each partition containing only one process.

The OS keeps a table recording which parts of memory are available and which parts are occupied.

We call a large available block of memory a "hole"; as memory allocation proceeds, multiple holes will appear in memory (the blue areas in the figure below).

When existing memory cannot meet the requirements of a process, one of the following methods can be adopted:

  • Reject the later process and provide an appropriate error message

  • Place the later process in a waiting queue; when memory is released later, the OS checks the waiting queue and determines whether the currently available memory meets the process's requirements

Generally speaking, the available memory blocks consist of a set of variable-length holes scattered throughout memory.

  • When a process arrives and needs memory, the OS finds a hole among these holes that is large enough

  • If the hole is too large, it splits the hole into two parts, giving one part to the process and keeping the other part as a hole

  • When a process terminates, it releases its memory block, and that block becomes a hole again

  • The newly created hole merges with adjacent holes into a larger hole

The above process is a dynamic storage-allocation problem. For this problem, the following possible strategies exist:

  • First fit: allocate the first hole that is large enough

  • Best fit: allocate the smallest hole that can satisfy the requirement

  • Worst fit: allocate the largest hole

Simulation results show that first fit and best fit perform better than worst fit in both time and storage efficiency. The first two are comparable in performance, but first fit is usually faster.

2.3 Fragmentation

First-fit and best-fit both suffer from the problem of external fragmentation:

  • When processes are loaded into and removed from memory, free memory space becomes split into multiple small pieces.

  • External fragmentation occurs when the total amount of memory space is sufficient to meet the needs of a process, but the available space is not contiguous (it is divided into multiple holes).

  • Another factor affecting the amount of external fragmentation is which end of a free block is allocated.

  • The severity of the external fragmentation problem depends on the total amount of memory storage and the average process size.

  • Statistics show that for first-fit, even with some optimization techniques, given N allocated blocks, 0.5N blocks are lost to fragmentation; this property is called the 50-percent rule.

For the external fragmentation problem, we have the following solutions:

Compaction

  • The goal is to rearrange the contents of memory so that all free memory is placed in one large block.

  • However, this method is not always effective — if relocation is static and is done at assembly or load time, compaction cannot be performed.

  • That is, compaction can be used only when relocation is dynamic and is done at execution time.

  • The simplest compaction algorithm is to move all processes to one end of memory and all holes to the other end, but this is costly.

Paging

  • It allows the physical address space of a process to be noncontiguous, so as long as memory is available, physical memory can be allocated to a newly arriving process.

  • Paging requires cooperation between the OS and the computer hardware.

  • This method is the most commonly used memory management technique and will be described in detail below.

Memory fragmentation can also occur internally. Physical memory is generally divided into fixed-size blocks, and memory is then allocated in units of blocks. Doing so causes the memory allocated to a process to be slightly larger than the memory it needs, and this unused memory corresponds to the problem of internal fragmentation.

3 Paging

3.1 Basic Method

The basic method for implementing paging is to divide physical memory into fixed-length blocks called "frames" and logical memory into fixed-length blocks called "pages." When a process executes, its corresponding logical pages are loaded into any available memory frames. Backing storage is likewise divided into fixed-length blocks of the same size as memory frames.

A logical address is divided into two parts:

  • Page number p: used as an index into the page table of each process. The page table contains the base address of each frame in physical memory.

  • Page offset d: the location within the referenced frame.

The paging model is as follows:

The steps by which the MMU translates a logical address into a physical address:

  1. Extract the page number p and use it as an index into the page table.

  2. Extract the corresponding frame number f from the page table.

  3. Replace p in the logical address with f.

As can be seen, the offset d remains unchanged.

The page size is defined by the hardware and is usually a power of 2, ranging roughly from 4 KB to 1 GB depending on the specific computer architecture. The reason for using a power of 2 is that it facilitates converting a logical address into a page number and a page offset. If the logical address space size is 2^m and the page size is 2^n bytes, then the high m - n bits of the address are designated as the page number, and the low n bits are the page offset.

The reader may notice that paging itself is a form of dynamic relocation: each logical address is bound to some physical address by the paging hardware, similar to memory frames using a base (or relocation) register.

Using a paging scheme avoids external fragmentation, but internal fragmentation may still occur. If a process size is unrelated to the page size, then on average half of each process's pages will suffer from internal fragmentation. This suggests that a smaller page size may reduce the impact of this problem, but it introduces additional overhead. Moreover, larger pages are more helpful for tasks such as disk I/O. Therefore, in modern computers, common page sizes are 4 KB and 8 KB; and some CPUs and systems support multiple page sizes.

Each page of a process requires a frame, so if a process requires n pages, then there must be at least n available frames in memory, as shown below:

Paging technology allows a clear separation between the programmer's view of memory and the actual physical memory: the programmer views memory as a single space containing only a certain program; in reality, user programs are scattered throughout physical memory.

The bridge that establishes these two understandings is the hardware used for address translation.

Since the OS manages physical memory, it must keep track of physical memory allocation information, and this information is kept in a simple system-wide data structure called the frame table. Each entry of the frame table corresponds to a physical frame, indicating whether it is free or allocated, and, if allocated, information about the process to which it is allocated.

The OS maintains a copy of each process's page table for translating logical addresses into physical addresses. The page table is also used by the CPU dispatcher to define the hardware page table, and thus paging increases context-switch time.

3.2 Hardware Support

Since the page table is a preprocessed data structure, a pointer to the page table is stored in a register located in the PCB.

Page tables are implemented in hardware in various ways. The simplest is to implement the page table using a set of dedicated high-speed hardware registers, which makes address translation very efficient. However, doing so increases context-switch time, because each register must be swapped (saved + restored) during a context switch. This approach is fine if the page table is small enough; but modern CPUs support much larger page tables, so this approach is not reasonable for these machines.

In practice, page tables are generally stored in main memory, with a page-table base register (PTBR) pointing to the page table. Switching page tables requires only changing this register, thus greatly reducing the impact on context-switch time.

However, we know that accessing memory takes considerable time; moreover, with paging, each data access requires two memory accesses (access the page table + access physical memory). The standard solution is to introduce a special small cache for fast lookup, called a translation look-aside buffer (TLB).

TLB entry lookup is part of the modern hardware pipeline and thus incurs no additional performance penalty.

To achieve lookup within the pipeline, the TLB must be small enough.

Some CPUs implement separate TLBs for data addresses and instruction addresses, thereby doubling the available TLB entries.

Current CPUs already have multi-level TLBs.

The TLB contains only a small number of page-table entries; when the CPU generates a logical address, the MMU checks whether the page number exists in the TLB.

  • If found, the frame number is immediately available for memory access.

  • If not found (i.e., a TLB miss), address translation must be performed as described earlier, and the page number and frame number must also be added to the TLB for future references.

If the TLB is full, an entry must be chosen for replacement; the replacement policy can be LRU, RR, or random replacement.

Some TLBs allow certain entries to be wired down, i.e., they cannot be removed from the TLB; TLB entries for critical kernel code fall into this category.

Some TLBs store an address-space identifier (ASID) for each entry; each ASID uniquely identifies a process and is used to provide protection for that process's address space.

  • When the TLB attempts to resolve a virtual page number, it needs to ensure that the ASID of the currently running process matches the ASID associated with the virtual page; if they do not match, a TLB miss occurs.

  • ASIDs allow the TLB to simultaneously contain page-table entries from different processes.

  • If the TLB does not support ASIDs, then the TLB contents must be flushed each time a new page table is selected, ensuring that the next executing process does not use incorrect translation information.

3.3 Protection

In memory using paging, protection is implemented by setting protection bits for each frame; these bits are usually placed in the page table. These bits can define the read-write state of a page as read-write or read-only. If an attempt is made to write to a read-only page, a hardware trap is triggered.

In addition, we can set a valid-invalid bit:

  • When this bit is set to valid, the associated page is in the process's logical address space and is therefore a valid page.

  • When this bit is set to invalid, the associated page is not in the process's logical address space.

Few processes use the entire address range; most of the time, only a small portion of the addresses is available. In this case, creating a page table for every page is rather wasteful, so some systems support a hardware register called the page-table length register (PTLR) to indicate the page table size, which is used to check each logical address to verify whether the address is within the process's valid range.

3.4 Shared Pages

One advantage of paging is that it makes it possible to share common code, which is especially important in a multiprocess environment. Take the Linux system as an example: most user processes require the standard C library libc.

If each process loads a copy of libc into its own address space, then when the number of processes increases, these copies will occupy a large amount of memory space.

Reentrant code is non-self-modifying code, that is, it does not change during execution, so multiple processes can execute this code simultaneously.

In addition to runtime libraries such as libc, other heavily used programs can also be shared, such as compilers, window systems, database systems, and so on.

4 Structure of Page Table

4.1 Hierarchical Paging

Most modern computers support very large logical address spaces, so the page table would be very, very large, and therefore the page table cannot be directly allocated contiguously in memory. A simple solution is to divide the page table into smaller blocks (assuming the page size is 4 KB (corresponding to a 12-bit page offset)).

However, for 64-bit logical addresses, if the page size is still 4 KB, then the original page number length is 52 bits; therefore, if the page number is divided into only two parts, the page table may still occupy a very large amount of space, so further division is needed (for example, three-level / four-level ...).

But doing so makes the page table structure very complex, which is why in 64-bit architectures this kind of hierarchical page table is usually unsuitable.

4.2 Hashed Page Tables

An alternative approach is to use a hashed page table.

  • The virtual page number is represented by a hash value.

  • Each entry in the hash table contains a linked list, and all elements in the same linked list have the same hash value.

  • Each element contains 3 fields: the virtual page number, the value of the mapped page frame, and a pointer to the next element in the linked list.

The general idea of the algorithm is:

  • The virtual page number in the virtual address is hashed onto the hash table.

  • The virtual page number is compared with the first field of the first element in the linked list. If they match, the corresponding page frame (the second field) is used to form the intended physical address; if they do not match, the search continues with the subsequent elements in the linked list.

A variant of the hashed page table is called the cluster page table. It is similar to the hashed page table, except that each entry in the hash table refers to multiple pages rather than a single page. This structure is useful when the address space is sparse (memory references are not contiguous and are scattered throughout the address space).

4.3 Inverted Page Tables

One disadvantage of page tables is that they may contain thousands of entries, thus occupying a large amount of physical memory just to track usage information of other physical memory. To solve this problem, we introduce the inverted page table.

Each entry of the inverted page table corresponds to each real page (or frame) of memory, consists of the virtual address of the page located at the actual memory location, and holds the process information for that page.

Therefore, there is only one page table in the entire system, and there is only one entry for each physical memory page.

An inverted page table usually requires an address space identifier (ASID), stored within each entry of the page table, to ensure that the logical address of a specific process is mapped to the corresponding physical page frame.

Although this scheme reduces the amount of memory required to store each page table, it increases the time required to look up the page table when a page reference occurs, because the inverted page table is sorted by physical address, but lookups occur on virtual addresses. To mitigate this problem, a hash table can be used to limit the search to one or a few page table entries. However, each access to the hash table adds an extra memory reference.

When shared memory exists, the inverted page table cannot be used, because one physical page cannot correspond to multiple shared virtual addresses.

5 Swapping

A process (or part of a process) can be temporarily swapped from memory to a backing store, and later returned to memory to continue execution, as shown below:

Swapping technology makes it possible for the address spaces of all processes to exceed the actual physical memory size, thereby increasing the degree of multiprogramming.

5.1 Standard Swapping

The standard swap operation allows complete processes to move between main memory and the backing store.

The backing store must be large enough to hold the entire process that needs to be stored and retrieved, and must provide direct access to memory.

When a process or part of it is swapped to the backing store, the data structures associated with the process must be written to the backing store.

For multithreaded processes, the data structures of each thread must also participate in swapping.

The OS must maintain metadata for swapped-out processes so that context information can be restored when these processes return to memory.

The advantage of this method is that it enables overcommitment of physical memory, allowing the system to accommodate more processes than the actual physical memory.

Idle or mostly idle processes are well suited to being swapped to the backing store.

5.2 Swapping with Paging

In contemporary OSs, the standard swapping described above is rarely used because the time cost of moving entire processes back and forth between memory and backing store is too high.

Therefore, most systems adopt a variant approach, namely swapping processes by page.

In practice, we usually use "swapping" to refer to standard swapping and "paging" to refer to "swapping with paging."

The page out operation moves a page from memory to backing store, and the reverse process is called page in.
