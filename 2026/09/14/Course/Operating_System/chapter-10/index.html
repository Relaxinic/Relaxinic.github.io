Virtual memory is a technique that allows the execution of a process without it being entirely in memory. A major advantage of this technique is that it allows programs to be larger than physical memory, because virtual memory abstracts main memory into a very large and uniform storage array.

1 Background

We do not need to place the entire program in memory for execution, for example in the following cases:

  • Code in the program used to handle infrequent errors

  • Data structures such as arrays and lists are often allocated more memory than they actually need

  • Some options or features in the program are rarely used

If parts of a program can be executed in memory, the following benefits are obtained (for both users and the system):

  • Programs are no longer constrained by available physical memory; users can write programs on a very large virtual memory, thereby simplifying the programming task

  • Because each program occupies less physical memory, more programs can be executed simultaneously, increasing CPU utilization and throughput without increasing response or turnaround time

  • Less I/O is needed to load or swap parts of programs, so programs run faster

A process's virtual address space is the logical (or virtual) view of how a process is stored in memory.

  • The heap space grows upward and is used for dynamic memory allocation

  • The stack space grows downward and is used for successive function calls

  • There is a large space (or hole) between the heap and the stack, so the virtual address space is a sparse address space; this characteristic is beneficial because when the stack or heap segment grows, the hole can be filled; and this hole can be used during program execution to hold dynamic link libraries (or possibly other shared objects)

In addition to separating logical memory from physical memory, virtual memory allows files and memory to be shared by multiple processes. This brings the following benefits:

  • System libraries such as the standard C library can be shared by multiple processes by mapping shared objects into the virtual address space

  • Memory can be shared between processes

  • When creating a process, pages can be shared through the fork() system call, thereby speeding up process creation

2 Demand Paging

Demand paging is a commonly used technique in virtual memory, where pages can be loaded on demand during execution; pages that are never accessed will not be loaded into physical memory.

2.1 Basic Concepts

When using demand paging, it is necessary to know whether a page is in memory or in secondary storage, so some hardware support is required. The valid bit introduced earlier can be useful here, but the concept of "valid" needs to be redefined: a page is valid only when it is legal and located in memory. So even if a page is legal, if it is in secondary storage, it is not valid.

When an invalid page is accessed, the MMU triggers a page fault. The OS handles a page fault as follows:

  1. Check the process's internal table (usually located in the PCB) to determine whether the current reference is a valid or invalid memory access.

  2. If the reference is invalid, terminate the process; if the reference is valid but the page has not yet been brought into memory, bring it in.

  3. Find a free frame (obtained from the free-frame list).

  4. Schedule a secondary storage operation to read the required page into the newly allocated frame.

  5. When the read operation completes, modify the process's internal table and page table to indicate that the required page is now in memory.

  6. Restart the instruction that was interrupted by the trap; the process can now access the required page (as if the page had always been in memory).

Pure demand paging: pages are not placed into memory unless required.

Therefore, when a process first starts executing, it has no pages, and page faults may occur repeatedly before the required pages are gradually loaded into memory.

In theory, some programs may access several new pages of memory on each instruction execution (one page for the instruction and multiple pages for data), so it is possible for every instruction to cause multiple page faults, which would obviously severely degrade system performance. In practice, however, this behavior rarely occurs because programs tend to exhibit locality of reference.

Hardware that supports demand paging includes:

  • Page table: each entry can mark a page as valid/invalid through a special value of the valid bit or protection bit.

  • Secondary memory: memory that holds pages not in main memory, usually a high-speed disk or NVM device; the portion used for swapping is the swap space.

A key requirement of demand paging is the ability to restart an instruction after a page fault. Because the state of the interrupted process is saved when the page fault occurs, it must be possible to restart the process at the same location and in the same state. In most cases, this requirement is easy to satisfy. One major difficulty is that an instruction may have modified values in multiple locations.

  • For example, the MVC (move character) instruction of the IBM System 360/370 can move up to 256 bytes from one location to another (possibly overlapping) location.

  • If either block (source or destination) crosses a page boundary, a page fault may occur after part of the move has completed.

  • In addition, if the source and destination blocks overlap, the source block may already have been modified, in which case the instruction cannot simply be restarted.

Solutions to this problem include:

  • Microcode computes and attempts to access both ends of both blocks; if a page fault is going to occur, it will occur during this step (before anything has been modified).

  • Temporary registers are used to store the values at the locations to be overwritten; if a page fault occurs, all old values will be written back to memory before the trap occurs.

2.2 Free-Frame List

To handle page faults, the OS maintains a free-frame list containing all free frames (also used when expanding the stack and heap segments). The OS usually allocates free frames using a technique called zero-fill-on-demand, that is, clearing the original contents of a frame before allocating it.

2.3 Pereformance

Demand paging greatly affects the performance of computer systems. To understand this, first calculate the effective access time required for demand paging. Let mamama be the memory access time, and ppp be the probability of a page fault occurring (0≤p≤10 \le p \le 10≤p≤1), then the effective access time is:

effective access time=(1−p)×ma+p×page fault time\text{effective access time} = (1 − p) \times ma + p \times \text{page fault time}effective access time=(1−p)×ma+p×page fault time

So we also need to know the time required to handle a page fault. The following are the main components affecting this time: page-fault interrupt handling, reading the page, and restarting the process.

The first and third points can be reduced to a few hundred instructions by carefully writing code. The key is the second point, which is greatly related to the storage device (queuing time waiting to use the device is not considered here). If mamama is on the order of nanoseconds, while disk access time is on the order of milliseconds, then it is obvious that the effective access time will be directly proportional to the page-fault rate. Therefore, in demand paging, reducing the page-fault rate is very important.

The handling and overall use of swap space must also be considered.

Input/output to swap space is usually faster than input/output to the file system.

One way to improve paging throughput is to copy the entire file image to swap space when the process starts, and then perform demand paging from swap space (obviously the copy cost is too high).

The method actually used is to initially perform demand paging on the file system, and write pages to swap space when they are replaced.

Some systems try to limit the amount of swap space used by performing demand paging on binary executable files. But when page replacement occurs, these frames are directly overwritten. With this method, the file system appears to be backing store. However, swap space must still be used to handle pages unrelated to files (called anonymous memory).

3 Copy-on-Write

Process creation using the fork() system call may initially bypass the need for demand paging through the use of a technique similar to page sharing. This technique provides rapid process creation and minimizes the number of pages that must be allocated to new processes. This technique is called copy-on-write (COW), which allows the parent process and child process to share the same pages. These shared pages that need to be modified are marked as copy-on-write pages; when a process writes to such a page, a copy of this shared page is created, and the write operation occurs only on this copy.

Some UNIX versions provide a variant of the fork() system call called vfork() (virtual memory fork).

Unlike fork() with copy-on-write, when using vfork(), the parent process is suspended, and the child process uses the parent process's address space.

Special care must be taken when using vfork(), because any changes made by the child process will be seen by the parent process. vfork() is generally used in cases where the child process immediately calls exec() after creation. It is much more efficient than fork().

4 Page Replacement

4.1 Basic

  1. If there is no free frame, find a frame that is currently unused and release it.

  2. The release operation can be implemented by writing the contents of the frame to swap space and modifying the page table to indicate that the page is no longer in memory.

  3. The process can now place the page in the frame that was just released.

Combining existing page replacement strategies, we modify the original page fault handling process as follows:

  1. Find the location of the required page in secondary storage.

  2. Find a free frame. If there is a free frame, use it; if not, use a page replacement algorithm to select a victim frame, write the victim frame to secondary storage (if necessary), and modify the page table and frame table.

  3. Read the required page into the newly freed frame; modify the page table and frame table.

  4. Continue executing the process from the point where the page fault occurred.

Note that if there is no free frame, two page transfers are required, which doubles the page fault handling time and increases the effective access time. We can reduce this overhead by using a modify bit (or dirty bit).

  • When any byte of a page is written, the hardware sets the modify bit, indicating that the page has been modified.

  • When selecting a page to be replaced, the modify bit needs to be checked. If the modify bit is set, the page must be written to secondary storage; if the modify bit is not set, it does not need to be written to secondary storage, and its contents can be overwritten directly.

This scheme can significantly reduce the time required to handle page faults, because when a page has not been modified, it can cut the I/O time in half.

When choosing a replacement algorithm, we usually want to obtain the lowest page fault rate. One evaluation method is to run the algorithm on a specific sequence of memory references and count the number of page faults. This sequence is called a reference string. A reference string can be generated artificially (using a random number generator, etc.) or obtained by tracing a specific system and recording the address of each memory reference.

However, the latter usually produces a large amount of data. To reduce the amount of data, we use two facts:

  • For a given page size, we consider only page numbers rather than complete addresses.

  • If page p is to be referenced, then any immediately following reference to page p will never cause a page fault; that is, after the first reference, page p will remain in memory.

4.2 FIFO

The simplest page replacement algorithm is the first-in, first-out (FIFO) algorithm. Implementation methods include:

  • Keep track of the time for each page; when a page needs to be replaced, choose the oldest one among them.

  • In fact, there is no need to keep track of the time for each page. You can create a FIFO queue to maintain the pages in memory. The page to be replaced is at the front of the queue, and new pages are inserted at the back of the queue.

Although this algorithm is easy to understand and implement, it performs poorly because it is very likely to evict a variable that was initialized a long time ago but will be heavily used after a long time.

The unexpected situation in which the number of page faults increases as the number of allocated frames increases is called Belady's anomaly.

4.3 Optimal

The algorithm that can achieve the lowest page fault rate and will never exhibit Belady's anomaly is the optimal page replacement algorithm, called OPT or MIN. Its idea is to replace the page that will not be used for the longest time (considering future usage).

Unfortunately, this algorithm is difficult to implement because in practice it is impossible to know the future information of the reference string in advance. Therefore, this algorithm is only used for comparative studies.

4.4 LRU

If recent past is used as an approximate value of near future, it replaces the most unused page so far (considering past usage). The method is the least recently used (LRU) algorithm.

LRU strategy is a commonly used page replacement algorithm, and it performs well. The main problem of LRU replacement is how to achieve it: it may require great hardware support and need to determine the order of the frames sorted by the last use time. There are the following two feasible implementation methods:

Counter(counter)

  • Associate a time-of-use field for each page table item and add a logical clock or counter to the CPU, which will increase each time memory reference.

  • Whenever a page is referenced, the content of the clock register will be copied to the usage time field in the page table item of the page.

  • In this way, we can always get the "time" of the last quote on each page.

  • The replaced page will be the page with the smallest time value.

  • This scheme needs to search the page table to find the LRU page and write it to the memory at each memory access (to the usage time field in the page table)

  • When the page table is changed (due to CPU scheduling), these times must also be maintained.

  • At the same time, the problem of clock overflow must be considered.

Stack

  • Maintain a stack with a record page number. Whenever a page is quoted, it will be removed from the stack and put at the top.

  • In this way, the recently used page is always at the top of the stack, and the least used page is always at the bottom.

  • Since the entry must be removed from the middle of the stack, it is best to use a two-way linked list with head pointers and tail pointers. In the worst case, six pointers need to be changed to remove a page X and put it at the top of the stack (two pointers of X, one pointer for each page before and after X, one pointer and a head pointer on the top page of the original stack). The cost of each update is slightly higher, but there is no need to search. The tail pointer points to the bottom of the stack, that is, the LRU page.

  • This method is especially suitable for LRU replacement algorithms implemented by software or microcode.

There will be no Belady exception in LRU replacement. It and the optimal page replacement algorithm belong to the stack algorithm, that is, it can be proved that the memory page set of n frames is always a subset of the page set in memory with n + 1 frames (therefore, when the number of frames increases, the original page in memory can still be retained, so it is not It will increase the number of page errors).

4.5 LRU-Approximation

From the above analysis, it is not difficult to see that implementing LRU is very costly, so few computer systems provide a true LRU page replacement algorithm. However, most systems provide a reference bit: it is cleared to zero during initialization; when a page is referenced, this bit is set by the hardware. We can use the reference bit to implement an approximate LRU algorithm.

Additional-Reference-Bits Algorithm

We can obtain additional page information by periodically recording the reference bit.

Keep one byte (8 bits) for each page.

After a fixed time interval, a timer interrupt transfers control to the OS; the OS places each page's reference bit in the most significant bit of its 8-bit byte, shifts the other bits one position to the right, and discards the least significant bit.

The 8-bit number in the shift register represents the history of page usage over the past 8 time periods.

A shift register of 00000000 indicates that the page was not used during the eight time periods.

For a page used at least once in each period, the value of its shift register is 11111111.

If this byte is interpreted as an unsigned integer, then the page with the smallest number (meaning it has been used the least in the most recent 8 time periods) is the LRU page that can be replaced.

Note: These numbers are not guaranteed to be unique. If multiple minimum values occur, either all pages with the minimum value can be replaced, or the FIFO method can be used to select among them.

Second-Chance Algorithm

The second-chance replacement algorithm is a FIFO replacement algorithm.

When selecting a page, we check its reference bit. If the value of the reference bit is 0, page replacement is performed; but if the value of the reference bit is 1, the page is given a second chance, and we continue to select the next FIFO page.

When a page gets a second chance, its reference bit is cleared, and its arrival time is reset to the current time.

Therefore, a page that gets a second chance will not be replaced until all other pages have been replaced (or given a second chance).

Furthermore, if a page is used frequently enough to keep its reference bit set, it will never be replaced.

One way to implement this algorithm (sometimes called the clock algorithm) is to use a circular queue.

  1. The pointer points to the next page to be replaced.

  2. When a frame is needed, the pointer moves forward until it finds a page whose reference bit is 0.

  3. During this process, it clears the reference bits it scans to 0.

  4. Once a page meeting the requirement is found, that page is replaced; the new page is inserted into the circular queue at the position of the original victim page.

In the worst case, when all bits are set to 1, the pointer will traverse the entire queue, giving every page a second chance, and at this point the algorithm degenerates to FIFO replacement.

Enhanced Second-Chance Algorithm

We can enhance the second-chance algorithm by treating the reference bit and the modification bit as an ordered pair. These two bits form four categories:

  1. (0, 0): Neither used nor modified -> the most suitable page to replace

  2. (0, 1): Not used recently, but modified -> less suitable for replacement, because its contents must be written to swap space before replacement

  3. (1, 0): Used recently, but not modified -> may be used again

  4. (1, 1): Used recently and modified -> may be used again, and its contents must be written to swap space before replacement

Each page belongs to one of these four categories.

When page replacement is needed, we use the same scheme as the clock algorithm, but at this point we check the category to which the page belongs.

We replace the first page encountered in the lowest non-empty category; multiple scans of the circular queue may be needed to find a page to replace.

The main difference between this algorithm and the simpler clock algorithm is that priority is given to pages that have been modified, in order to reduce the number of required I/O operations.

4.6 Counting-Based

We can also use a counter to record the number of references to each page to implement page replacement:

Least frequently used (LFU) page replacement algorithm: replace the page with the fewest references.

The reason for choosing this kind of page is that a page in active use should have a relatively large reference count.

However, a problem arises when a page is heavily used during the initial phase of a process but is never used again afterward: because it was once heavily used, it has a large count, and even if it is no longer needed, it still remains in memory.

One solution is to shift the count right by 1 bit at regular intervals, thereby forming an exponentially decaying average use count.

Most frequently used (MFU) page replacement algorithm

Its design is based on the argument that the page with the fewest references may have just been brought in and has not yet been used.

However, neither of these two replacement methods is a common approach, because they are costly to implement and do not approximate the OPT replacement well.

4.7 Page-Buffering

The system typically maintains a pool of free frames; when a page fault occurs, a victim frame is selected as before.

  • However, before writing out the victim page, the needed page is read into a free frame from the pool.

  • This process allows the process to restart as quickly as possible without waiting for the victim page to be written out.

  • When the victim page is later written out, its frame is added to the free frame pool.

An extension of this idea is to maintain a list of modified pages.

  • Whenever the paging device is idle, a modified page is selected and written to secondary storage, and then its modified bit is reset.

  • This scheme increases the probability that, when a victim page is selected, the page is clean and does not need to be written out.

Another modification is to keep a set of free frames but remember the page that each frame contains.

  • Since the contents of a frame are not modified when it is written to secondary storage, if the old page is needed again before that frame is reused, it can be reused directly from the free frame pool without requiring I/O.

  • When a page fault occurs, first check whether the needed page is in the free frame pool; if not, a free frame must be selected and the page read into it.

4.8 Applications

In some cases, applications that access data through the OS's virtual memory perform worse than when the OS does not provide buffering.

A typical example is a database, which provides its own memory management and I/O buffering.

Another example is that data warehouses often perform large-scale sequential storage reads, followed by computation and writes.

The LRU algorithm will evict old pages and retain new pages, whereas the application is more likely to read older pages rather than newer ones (because it starts sequential reading again).

In this case, MFU would actually be more effective than LRU.

Such applications understand their memory usage and storage usage better than an OS implementing a general-purpose algorithm.

Furthermore, if the OS is performing I/O buffering and the application is also doing so, then twice the memory will be used for a set of I/O operations.

Due to these issues, some OSes allow specific programs to use a secondary storage partition as a large array of sequential logical blocks without any file system data structures. This array is sometimes called a raw disk; I/O to this array is called raw I/O, and it can bypass all file system services.

Note that although some applications are more efficient when implementing their own specialized storage services on raw partitions, most applications perform better when using regular file system services.

5 Allocations of Frames

5.1 Minimum Number of Frames

The frame allocation strategy is constrained by multiple factors. For example, the number of allocated frames must not exceed the maximum number of frames (unless page sharing exists), and there is also a minimum requirement for the number of allocated frames. The former is obvious, so let us look at what the latter is about.

One reason for determining the minimum allocation amount is performance considerations. Obviously, the fewer frames allocated to each process, the higher the page fault rate will be, thereby reducing program execution speed. Therefore, there must be enough frames to hold all the pages.

The minimum number of frames depends on the computer architecture (different addressing modes, etc.), while the maximum number depends on the available physical memory.

5.2 Allocation Algorithms

If we want to allocate a total of m frames to n processes, the simplest method is equal allocation, that is, each process gets m / n frames.

The second method is based on an observation: different processes require different amounts of memory. For example, some processes require far fewer frames than the average, so using the previous method would waste many frames. To solve this problem, we use a method called proportional allocation, which allocates memory based on process size. Let the virtual memory size of process pip_ipi​ be sis_isi​, and let the total number of available frames be mmm. Define S=∑siS = \sum s_iS=∑si​ as the total size. Then the number of frames allocated to process pip_ipi​ is approximately:

ai=si/S×ma_i = s_i / S \times mai​=si​/S×m

It is necessary to ensure that aia_iai​ is an integer greater than the minimum number of frames required by the instruction set and does not exceed mmm.

In the first two allocation algorithms, the specific allocation will also change with the degree of multiprogramming. Moreover, regardless of which algorithm is used, high-priority and low-priority processes are treated equally, but obviously we want high-priority processes to receive more memory in order to speed up execution. One solution is: in proportional allocation, the proportion of frames no longer depends on process size, but is based on process priority, or a combination of both.

5.3 Global v.s. Local Allocation

Another factor affecting frame allocation is page replacement. We can divide page replacement into two major categories:

Global replacement: allows a process to select a victim frame from the frames of all processes, even if that frame belongs to another process; therefore, one process can preempt the frames of other processes.

Local replacement: each process can select only from its own set of frames.

One problem with the global replacement algorithm is that a process's memory pages depend not only on that process's paging behavior but also on the paging behavior of other processes. Therefore, even the same process can have different execution results. The local replacement algorithm does not have this problem, but it may block a process because it does not provide it with other less frequently used memory pages. Therefore, global replacement usually has higher throughput and thus has become the most commonly used method.

Next we consider only global page replacement strategies. This method can satisfy all memory requests from the free frame list, but instead of starting to select victim pages before free memory drops to zero, it triggers page replacement when free memory drops below a certain threshold, ensuring that there is always enough free memory to satisfy new requests. The process is as follows:

When it drops below the threshold, a kernel routine (called the reaper) is triggered and begins to reclaim pages from all processes.

The reaper routine can adopt any of the page replacement algorithms introduced earlier, but some approximate LRU algorithm is commonly used.

When the amount of free memory reaches the maximum threshold, the reaper process suspends and continues only when free memory drops to the minimum threshold.

In Linux, if the amount of free memory becomes very, very low, a routine called the "out-of-memory (OOM) killer" selects a process to terminate, thereby freeing its memory.

Each process has an OOM score; a higher score means the process is more likely to be terminated by the out-of-memory killer.

The OOM score is calculated from the proportion of memory being used by the process; the higher the proportion, the higher the score.

5.4 Non-Uniform Memory Access

Until now, we have assumed that all main memory is equal; however, in non-uniform memory access (NUMA), the situation is different. In such systems, each CPU has its own local memory, and the CPUs are organized through a shared system interconnect. Obviously, a CPU accessing its own local memory will be faster than accessing the local memory of other CPUs.

Therefore, managing which frames are placed in which locations greatly affects the performance of NUMA systems. If all memory is still treated equally, a CPU may spend longer waiting. So for NUMA, our goal is to make the allocated memory frames as close as possible to the CPU on which the process is running (that is, to minimize latency).

At the same time, the scheduler must track the CPU on which each process last ran, so that the virtual memory system can try to allocate frames to each process as close as possible to the process's CPU, thereby improving cache hit rates and reducing memory access time.

If threads are also considered, the situation becomes even more complex. Linux's approach is:

  • Have the kernel identify the hierarchy of scheduling domains

  • The CFS scheduler does not allow threads to migrate between different domains, thereby avoiding memory access penalties

  • Linux also maintains a separate free frame list for each NUMA node, thereby ensuring that threads allocate memory from the node on which they are running

6 Thrashing

If a process does not have enough frames, it will soon experience page faults, and at this point it must replace some pages. However, since all pages are in use, it must replace a page that will be needed again very soon, so it will soon experience page faults again. Then it needs to replace pages again, page faults occur again, and this cycle repeats. This situation is called thrashing. At this time, a process spends more time on page swapping than on execution, that is, CPU utilization is extremely low while disk utilization is extremely high, which obviously leads to serious performance problems.

6.1 Cause of Thrashing

To increase CPU utilization and stop thrashing, the degree of multiprogramming must be reduced. Therefore, we adopt a local replacement algorithm (or priority replacement algorithm). In this case, if a process thrashes, it will not steal pages from other processes, thereby preventing other processes from thrashing.

But this is not enough. To prevent thrashing, the process must be provided with enough frames. One strategy is to define a locality model for a process during execution.

A "locality" is a set of pages that are actively used, defined by the program structure and data structures.

A process is usually composed of multiple different localities, and these localities may overlap.

For example, a function call creates a locality.

The following figure shows how the locality of a process changes over time (a set of pages enclosed in curly braces is a locality):

Suppose a process is allocated enough frames to accommodate its current locality. It will incur page faults for the pages in its locality until all these pages are in memory; after that, no more page faults will occur until its locality changes.

If enough frames are not allocated to accommodate the size of the current locality, the process will experience frequent page faults because it cannot keep all the pages in use in memory.

6.2 Working-Set Model

The working-set model is based on the assumption of locality. The parameter Δ\DeltaΔ is used to define the size of the working-set window, in order to detect references to the most recent Δ\DeltaΔ pages; these pages are the working set, that is, the set of pages currently being actively used. Therefore, the working set is an approximation of locality.

The accuracy of the working set depends on the choice of Δ\DeltaΔ.

  • If Δ\DeltaΔ is too small, it cannot contain the complete locality.

  • If Δ\DeltaΔ is too large, multiple localities may overlap.

The most important property of the working set is its size. Suppose the working-set size of each process is WSSiWSS_iWSSi​; then D=∑WSSiD = \sum WSS_iD=∑WSSi​ is the total number of frames required. If D>mD > mD>m (the total number of available frames), then thrashing will occur.

Once Δ\DeltaΔ is determined, using the working-set model is very simple.

The OS monitors the working set of each process and provides enough frames for the working set to satisfy its working-set size.

If there are enough extra frames, then other processes can be initiated.

If the working-set size increases beyond the total number of available frames, then the OS will select a process and suspend it; the pages of that process will be written out, and its frames will be reallocated to other processes, after which the process will be restarted.

The working-set strategy can avoid thrashing while allowing the degree of multiprogramming to be as high as possible, thereby optimizing CPU utilization.

The difficulty of this model lies in tracking the working set. We can approximate the working-set model using a timer interrupt at fixed intervals and a reference bit.

Suppose Δ\DeltaΔ = 10,000 references; then the timer interrupt can be triggered every 5,000 references.

When an interrupt occurs, copy and clear the reference bit of each page.

Therefore, when a page fault occurs, the current reference bit and two in-memory bits can be checked to determine which pages have been used in the most recent 5,000 references.

If a page has been used, then at least one bit is set, indicating that it is in the working set; if it has not been used, none of the bits are set.

The above arrangement is not accurate because we do not know exactly which of the 5,000 references occurred. However, uncertainty can be reduced by increasing the number of history bits and the interrupt frequency, although this brings higher cost.

6.3 Page-Fault Frequency

We want to control the level of the page fault rate because:

Too high -> the process needs more frames

Too low -> the process may have been allocated too many frames

So we need to set an upper bound and a lower bound for the required page fault rate, as shown in the figure:

If the page fault rate exceeds the upper bound, allocate more frames to the process.

If the page fault rate is below the lower bound, remove some frames owned by the process.

If the page fault rate is too high and there are no available frames, it may be necessary to select some processes and swap them out to backing storage.

7 Memory Compression

An alternative to paging is memory compression. With this approach, instead of swapping modified pages to swap space, the system compresses multiple pages into a single page, thereby enabling the system to reduce memory usage without performing page swapping.

Since mobile devices typically do not support paging, memory compression is an important part of memory management in most mobile operating systems.

Although memory compression does require allocating free frames to hold compressed pages, the results of compression algorithms show that this approach can indeed significantly save memory usage. However, in any form of data compression, there is always a trade-off between the speed of the compression algorithm and the reduction achieved by the compression implementation (i.e., the compression ratio). In addition, multiple cores help enable parallel execution of compression algorithms.

8 Allocating Kernel Memory

Typically, the OS allocates kernel memory from a free memory pool that is different from the one used to satisfy general user processes. This is because:

The kernel may request memory for data structures of varying sizes, and sometimes the size may be less than a single page. Therefore, the kernel must use memory carefully and try to minimize waste caused by fragmentation. This is very important because many operating systems do not perform paging system handling for kernel code or data.

Some hardware devices interact directly with physical memory, so they may require memory that exists in physically contiguous pages.

The following introduces some strategies for managing free memory allocated to kernel processes.

8.1 Buddy System

The buddy system allocates memory from fixed-size segments composed of physically contiguous pages. Memory is allocated from this segment using a power-of-2 allocator, which satisfies requests in units of power-of-2 sizes (4 KB, 8 KB, 16 KB, and so on). For larger memory requests, it rounds up to the next highest power of 2.

One advantage of the buddy system is that adjacent buddies can quickly form a larger segment through coalescing. For example, in the above example, when CLC_LCL​ is freed, CL,CRC_L, C_RCL​,CR​ can coalesce into a 64 KB segment BLB_LBL​. Then BLB_LBL​ and BRB_RBR​ can also coalesce into a 128 KB segment, eventually returning to a 256 KB segment.

However, an obvious disadvantage of this system is that rounding up to the next highest power of 2 is very likely to cause fragmentation within the allocated segment. In fact, there is no guarantee that no more than 50% of the allocated unit will be wasted due to internal fragmentation.

8.2 Slab Allocation

The second strategy is called slab allocation.

A slab consists of one or more physically contiguous pages.

A cache contains one or more slabs. Each kernel data structure has a unique cache, such as a separate cache for process descriptors, a separate cache for file objects, and so on.

A cache contains instantiated objects of the kernel data structure.

The following figure shows the relationship among these three:

When a cache is created, some initial objects marked as free are allocated to that cache.

The number of objects in a cache depends on the size of the associated slab.

Initially, all objects in the cache are marked as free.

When a new kernel data structure object is needed, the allocator can allocate any free object from the cache to satisfy the request; objects allocated from the cache are marked as used.

In Linux, a slab may be in one of the following states:

  • Full: all objects in the slab are marked as used

  • Empty: all objects in the slab are marked as free

  • Partial: the slab contains both used and free objects

The slab allocator first tries to use free objects in a partial slab to satisfy the request. If none exist, it allocates a free object from an empty slab. If no empty slab is available, it allocates a new slab from contiguous physical pages, assigns it to the cache, and then allocates memory for the object in this slab.

The benefits of the slab allocator include: no memory wasted due to fragmentation, and memory requests can be satisfied quickly.

The latest Linux distributions provide two new types of kernel memory allocators: SLOB and SLUB.

SLOB: an allocator designed for systems with a limited amount of memory, maintaining three object lists: small (< 256 B), medium (< 1024 B), and large (< 1 page).

SLUB: replaces SLAB as the default kernel allocator of Linux, greatly reducing overhead compared with SLAB.

9.3 TLB Reach

TLB reach is the amount of memory accessible from the TLB.

TLB reach = TLB size × page size

Ideally, the working set of each process is stored in the TLB; otherwise, a high frequency of page faults will occur.

Increasing the page size may lead to increased fragmentation, because not all applications need such large pages.

Solution: provide multiple page sizes, so that applications that need large pages can use larger page sizes without increasing fragmentation.
