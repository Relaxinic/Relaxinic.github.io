Chapter 1 Introduction

1.1 What Operating System Do

A complete computer system consists of the following parts:

Operating system: controls the hardware and coordinates its use among different application programs and among different users.

We adopt a relatively widely accepted definition: an operating system is a program that is always running on the computer, and this program is usually called the kernel. In addition, there are two other types of programs:

  • System program: related to the operating system, but not a necessary component of the kernel.

  • Application program: includes all programs unrelated to system operation.

For mobile operating systems, in addition to the kernel, there is also something called middleware, which is a set of software frameworks that provide additional services to application developers.

In summary, we consider the operating system to include an always-running kernel, middleware frameworks, and system programs. In addition, the focus of the later discussion is still on the kernel.

When a computer is powered on or restarted, the bootstrap program is loaded. The bootstrap program is stored in ROM or EPROM, which are usually called firmware. It initializes various aspects of the system, loads the operating system kernel, and starts executing it.

1.2 Computer-System Organization

A modern general-purpose computer system consists of one or more CPUs and some device controllers (each with a local buffer) connected through a common bus, providing access to components and shared memory.

The following will introduce three key aspects that keep a system running: interrupts, storage structures, and I/O structures.

Interrupts

Hardware can trigger an interrupt at any time by sending a signal to the CPU (usually via the system bus). When the CPU is interrupted, it stops what it is currently doing and immediately switches to executing the task at a fixed location (generally the starting address of an interrupt service routine). The timeline of an interrupt is as follows:

The interrupt service routine will call a specific interrupt handler. Since interrupts need to be handled quickly, a table of pointers (addresses) to interrupt routines is used. This table is generally stored in the low-address area of memory and is called the interrupt vector. Its address is then indexed by a unique number, which is provided with the interrupt request, to provide the address of the interrupt service routine for the interrupting device.

The interrupt architecture must also save the information at the time of the interrupt, and these pieces of information need to be restored after the interrupt routine is completed. If the interrupt routine needs to change the processor state, it must save the current state (by saving the values in the registers and the program counter), and later restore that state before returning. In addition, while handling another interrupt, incoming interrupts are disabled to prevent lost interrupts.

A trap is an interrupt generated by software, arising from an error during program execution or from an explicit user request (called a system call).

The basic interrupt mechanism works as follows:

  • When the CPU detects that the controller has signaled on the interrupt-request line, it reads the interrupt number and jumps to the interrupt-handler routine by using that interrupt number as an index into the interrupt vector.

  • During execution, the interrupt-handler routine saves any state that will be changed, determines the cause of the interrupt, performs the necessary processing, restores the state, and executes the return_from_interrupt instruction, causing the CPU to return to the execution state from before the interrupt.

In addition to the simple mechanisms described above, modern operating systems have more sophisticated interrupt-handling features provided by the CPU and interrupt-controller hardware:

  • Deferring interrupt handling during critical processing

  • Multiple levels of interrupts, so that the operating system can distinguish between high-priority and low-priority interrupts (interrupt priority levels) and respond with an appropriate degree of urgency

In summary, modern operating systems widely use interrupt mechanisms to handle asynchronous events. Device controllers and hardware faults trigger interrupts. Because interrupts are used extremely frequently in time-sensitive processing, efficient interrupt handling is crucial to ensuring system performance.

Interrupt Types

  • External Interrupts

    • Maskable interrupt: An interrupt requested to the processor via the INTR line, mainly from external devices such as hard drives, printers, network cards, etc. This type of interrupt does not affect system operation and can be handled at any time, or even not handled at all.

    • Non-maskable interrupt: An interrupt requested to the CPU via the NMI line. Sources: power failure, hardware circuit faults, etc. “Non-maskable” means it cannot be masked.

  • Internal Interrupts

    • Trap: An intentional, pre-arranged exceptional event. The CPU will invoke a specific program to handle it accordingly, and after handling is complete, return to the instruction following the trap instruction.

    • Fault: A type of unexpected event detected by the CPU when the instruction causing the fault has been executed but has not yet finished executing. When an error occurs, it is handed over to the fault handler for processing. If the error can be corrected, the CPU re-executes the instruction; if it cannot be handled, an error is reported. A common fault is a page fault.

    • Abort: A fatal error occurs during instruction execution that cannot be repaired, and the program cannot continue running and can only be terminated. This is usually caused by some hardware error.

Storage Structure

I/O Structure

Two I/O methods:

  • After I/O is started, control is returned to the user program only when the I/O is complete (synchronous). The wait instruction keeps the CPU idle until the next interrupt. Wait loop (memory access contention). At most one outstanding I/O request at a time, and simultaneous I/O processing is not allowed.

  • After I/O is started, control can be returned to the user program without waiting for the I/O to complete (asynchronous). System call: issues a request to the operating system, allowing the user to wait for I/O completion. The device-status table contains an entry for each I/O device, indicating its type, address, and status.

The interrupt-driven I/O loop introduced earlier is OK for small-scale data, but for large-volume data movement such as NVS (nonvolatile storage) I/O, it incurs significant overhead. The solution is to use DMA (direct memory access). After setting up the buffer, pointer, and counter, the device controller can transfer an entire block of data directly between the device and main memory without CPU intervention. Only one interrupt is generated per data block (previously, one interrupt was generated per byte) to notify the device driver that the operation is complete. While the device controller performs these operations, the CPU can do other work.

1.3 Computer-System Architecture

Depending on the number and organization of processors, several common types of computer system architectures are introduced below.

CPU: Hardware that executes instructions
Processor: A physical chip containing a single or multiple CPUs
Core: The basic computational unit of a CPU
Multicore: Containing multiple computational cores on the same CPU

Single-Processor Systems

Previously, most computer systems had only one processor, which also contained only a single-core CPU, and the core within it was the component that executed instructions and was used for local data storage. In addition to being able to execute general-purpose instruction sets, the core could also execute some special-purpose instruction sets, which came from device-specific processors (with limited instruction sets that do not run processes), including those of disks, keyboards, and graphics controllers, among others.

Multiprocessor Systems

Multiprocessor systems now dominate the entire field of computing. Traditionally, such systems contain two or more processors, each containing a single-core CPU. These processors share the computer bus and sometimes also share a clock, memory, and peripheral devices. The main advantage of this kind of system is increased throughput, that is, completing more work in a shorter time. It is worth noting that N processors do not bring an N-fold speedup, because there is additional overhead when multiple processors jointly complete a task.

The most common multiprocessor system is SMP (symmetric multiprocessing), in which each peer CPU processor executes all tasks, including operating system functions and user processes. The figure below shows an SMP architecture containing 2 processors:

The advantage of this architecture is that multiple processes can run simultaneously, meaning that if there are N CPUs, N processes can run without a significant drop in performance. The drawback is that because the CPUs are separate, there can be a situation where one CPU is idle while another CPU is running at full load, resulting in inefficiency. The solution is to reduce the workload disparity among processors by sharing processes and resources (such as memory).

The current definition of multiprocessor systems also includes multicore systems, which are more efficient than multi-chip designs using only single cores, because communication speed within a chip is higher than between chips, and they are more energy-efficient. The figure below shows a dual-core design on a single chip, and it can be seen that a two-level cache structure is used here.

Adding too many CPUs to a multiprocessor system will make contention on the system bus become a bottleneck, and performance will instead decline. An improvement is to equip each CPU (or group of CPUs) with its own local memory, accessed through a fast small local bus. These CPUs are connected through a shared system interconnect, so that all CPUs can share one physical address space. This approach is called NUMA (non-uniform memory access), and its architecture diagram is as follows:

The advantage of this architecture is that when a CPU accesses local memory, it is not only fast but also does not cause contention in the system interconnect. Therefore, as the number of processors increases, NUMA systems can become more efficient (which is why NUMA is becoming increasingly popular in servers and HPC). But its drawback is that CPUs must access remote memory through the system interconnect, and the extra time consumed harms performance. Fortunately, the operating system can minimize this loss caused by NUMA through careful CPU scheduling and memory management.

1.4 Operating-System Operations

Multiprogramming and Multitasking

An important characteristic of an operating system is the ability to run multiple programs; in addition, users usually want to run multiple programs at once—the technique for achieving this goal is multiprogramming. It improves CPU utilization by organizing jobs (including code and data) so that the CPU and I/O devices are always working. In a multiprogramming system, a program that is executing is called a process.

  • The operating system keeps several processes in memory at the same time, selects one of them, and begins executing it.

  • A process may need to wait for certain tasks to complete, such as I/O operations, at which point the CPU can switch to another process and execute it.

  • Eventually, the first process finishes waiting and regains CPU resources.

Multitasking is a logical extension of multiprogramming. In a multitasking system, the CPU executes multiple processes by switching among different processes. This switching occurs extremely frequently, thereby providing users with fast response times and enabling interactive computing. To ensure a reasonable response time (< 1s), a common approach is to use virtual memory, allowing users to run programs larger than actual physical memory. In addition, it abstracts main memory into a large, uniform array of storage, separating the logical memory seen by users from physical memory, so there is no need to worry about actual memory capacity limitations.

Having multiple processes in memory at the same time requires some form of memory management. In addition, if multiple processes are ready to run at the same time, the system must choose the next process to run. Making this decision is CPU scheduling. Finally, running multiple processes at the same time requires limiting their ability to affect one another at all stages of the operating system, including process scheduling, disk storage, and memory management.

Dual-Mode and Multimode Operation

To ensure the correct execution of the system, we must be able to distinguish between the execution of operating system code and user-defined code. The approach taken by most computer systems is to provide hardware support that allows different execution modes to be distinguished. Generally, at least two types of modes are distinguished (dual mode):

User mode: The CPU can only execute part of the instruction set and cannot directly access hardware resources; it is mainly used to run user programs.

Kernel mode (also called supervisor/system/privileged mode): The CPU can execute all instructions (including privileged instructions) and can access all hardware resources; it is mainly used to run the operating system kernel.

The specific operations involved are: memory management, process management, device driver management, and system calls, etc.

Generally, a mode bit in hardware is used to identify the current state (0 for kernel, 1 for user). When a user application requests a service from the operating system, the system must switch from user mode to kernel mode to complete the request. This process is shown in the figure below:

There can be multiple modes, for example:

  • Intel processors have four independent protection rings, where ring 0 is kernel mode and ring 3 is user mode (although rings 1 and 2 can theoretically be used for various operating system services, they are rarely used in practice).

  • The ARMv8 architecture has seven operating modes.

  • CPUs that support virtualization technology usually have a dedicated mode to indicate the virtual machine manager’s (VMM) control state over the system; in this mode, the VMM has higher privileges than user processes but lower than kernel privileges; it needs this privilege level to create and manage virtual machines and to perform related operations by modifying the CPU state.

A system call provides a way for a user program to request that the operating system perform tasks that are exclusive to the operating system on behalf of the user program. The specific manner in which a system call is invoked varies widely, depending on the features provided by the underlying processor. Typically, a system call is implemented in the form of a trap at a specific location in the interrupt vector. Although some systems have a dedicated syscall instruction to initiate a system call, this trap can also be executed through a general-purpose trap instruction.

When a system call is executed, it is usually treated by the hardware as a software interrupt. Control is transferred through the interrupt vector to the operating system’s service routine, and the mode bit is set to kernel mode. The system call service routine is part of the operating system. The kernel examines the interrupt instruction to determine which system call has occurred (an argument indicates the type of service requested by the user program). Other information needed for the request may be passed through registers, the stack, or memory. The kernel verifies that the arguments are correct and valid, executes the request, and returns control to the instruction following the system call.

Timer

Before transferring control to the user, the operating system ensures that the timer is set to interrupt. If the timer interrupts, control will automatically transfer back to the operating system, at which point the system may treat this interrupt as a fatal error or choose to extend the program’s running time. Obviously, instructions that modify the timer’s contents fall within the category of privileged instructions.

1.6 Three Conceptual Pieces

Virtualization

The OS takes physical resources and transforms them into a more general, more powerful, and easier-to-use virtual form (which is why the OS is sometimes called a virtual machine).

The OS provides interfaces (APIs) that can be invoked by users, and generally exposes hundreds of system calls to applications. Since the OS uses these calls to support program execution, memory and device access, and other related operations, we sometimes also say that it provides a standard library to applications.

Categories:

  • CPU virtualization: The system has a great many virtual CPUs, thus transforming a single CPU (or a small group of CPUs) into what appears to be an unlimited number of CPUs, so that many programs appear to run at the same time.

  • Memory virtualization: It is as if each running program has its own private memory (a virtual address space), rather than sharing the same physical memory with other running programs (in reality, the OS maps it in some way onto the machine’s physical memory).

Concurrency

This encompasses a series of problems that arise and must be solved when handling multiple things at the same time (that is, concurrently) within the same program.

Modern multi-threaded programs also have concurrency problems.

For now, we can regard a thread as a function running in the same memory space as other functions, with multiple threads active at the same time.

2.1 Operating-System Services

Although the specific services provided by different OSs vary, there are still some common services. The following briefly introduces them from the two perspectives of users and systems:

User

User interface:

  • Graphic user interface (GUI)

  • Touch-screen interface

  • Command-line interface (CLI)

Program execution: load into memory, run, (normal / abnormal) exit

I/O operations: for files or I/O devices

File-system manipulation:

  • Read and write files / directories

  • Create / delete / search / list files

  • Permission management

Communication:

  • Includes communication between different processes within the same computer, as well as communication between processes on different computer systems connected through a network

  • Implementation techniques: shared memory, message passing

Error detection:

  • Errors may occur at the hardware level (CPU, memory, I/O devices) or at the software level

  • Solutions: correct or terminate, and sometimes return an error code

System

Resource allocation:

  • Some resources may have special allocation code, while other resources may have more general request code and release code

Logging: usage statistics, tracking the use of computing resources, facilitating administrator configuration

Protection and security:

  • Protection: when multiple processes run concurrently, processes must not interfere with one another, which requires ensuring that all access to system resources is controlled

  • Security: requires users to verify their identity

2.2 User and Operating-System Interface

Command Interpreters

Compared with the term “command interpreters,” we may be more familiar with “shell”; in fact, the two are roughly equivalent. In Unix and Linux systems, the commonly used ones today are bash (Bourne-Again shell), zsh (Z shell), and fish (C shell and Korn shell are already rarely used). Readers can use the echo $e command to check the shell currently in use. For convenience in the following explanation, the term “command interpreter” will still be used below rather than “shell.”

As the name suggests, the main function of a command interpreter is to obtain and execute the next command specified by the user. These commands are roughly implemented in the following ways:

  • The command interpreter itself contains the code to execute commands.

  • Most commands are implemented through system programs (this is exactly what UNIX does).

Graphic User Interface

For the vast majority of users today, the first way they come into contact with a computer may be the GUI. Today’s mainstream operating systems all have their own GUIs. Even Linux, commonly used by programmers, has open-source desktop environments such as KDE and GNOME. So there is not much to say here.

Touch-Screen Interface

Today’s smartphones and tablets basically all use touch-screen interfaces.

2.3 System Calls

System calls provide an interface for accessing OS services. These calls are usually functions written in C and C++, but some low-level tasks may have to be written using assembly language instructions.

Application Programming Interface⚓︎

In fact, even a very simple program will make extensive use of the OS; moreover, the OS usually has to execute thousands of system calls per second. Most developers do not see these low-level details because they use an application programming interface (API) when designing programs, such as the Windows API, POSIX API, Java API, and so on. Programmers access the API through code libraries provided by the OS. For example, in UNIX and Linux systems written in C, such a library is libc. Behind the scenes, the functions that make up the API usually call the actual system calls on behalf of the application programmer.

The reason programmers prefer programming based on APIs rather than calling system calls directly is that using APIs has the following benefits:

Program portability: programs written using the same set of APIs can be compiled and run on systems with the same API. Compared with APIs, system calls are more complex and harder to work with.

Runtime environment (RTE): a complete set of software used to execute programs, including compilers, interpreters, libraries, loaders, and so on. The RTE provides a system-call interface as the link to the system calls provided by the OS. Usually, each system call is associated with a number, and the system-call interface maintains a table based on these numbers. It then invokes the expected system call in the operating system kernel and returns the status of the system call. Most details of the operating system interface are hidden by the API and managed by the RTE.

Common methods for passing parameters to the OS: pass parameters using registers; parameters are stored in memory in the form of a block or table, and the address of the block is passed to a register as a parameter; parameters are pushed onto a stack or popped from a stack.

Types of System Calls

Process control: create / terminate processes, load / execute, get / set process attributes, wait for events / send event signals, allocate / free memory

File management: create / delete files, open / close, read / write / reposition, get / set file attributes

Device management: request / release devices, read / write / reposition, get / set device attributes, logically attach or detach devices

Information maintenance: get / set time / date, get / set system data, get process / file / device attributes, set process / file / device attributes

Communication: create / delete communication connections, send / receive messages, transfer status information, connect / disconnect remote devices

Protection: get / set permissions

2.4 System Services

System services (also known as system utilities) provide a convenient environment for program development and execution. Some of them are simply user interfaces to system calls, while others are considerably more complex. They can be divided into the following categories:

  • File management: creation/deletion/copying/renaming/printing/listing, as well as general access to and manipulation of files/directories

  • Status information: date, time, available memory or disk space, number of users, or more complex detailed performance, logging, and debugging information. Some systems also support a registry for storing and retrieving configuration information

  • File modification: text editors, special commands for searching file contents or transforming text

  • Programming-language support: compilers, assemblers, debuggers, interpreters, etc.

  • Program loading and execution: once a program has been assembled or compiled, it must be loaded into memory in order to execute. The system may provide absolute loaders, relocatable loaders, linkage editors, and overlay loaders. Debugging systems for high-level languages or machine language are also needed

  • Communication: provides mechanisms for creating virtual connections among processes, users, and computer systems

  • Background services: continuously running system program processes are called services, subsystems, or daemons. A typical system has dozens of daemons. An OS that runs important activities in the user context rather than the kernel context may use daemons to perform these activities.

2.5 Linkers and Loaders

Normally, a program is stored on disk as a binary file (such as a.out or prog.exe). For the program to run on the CPU, it must first be loaded into memory and placed within the context of a process. The following figure summarizes this flow well:

  • Source files are compiled into object files that can be loaded into any physical memory location; this format is called relocatable object files.

  • Next, the linker combines these relocatable object files into a single binary executable file. During the linking phase, other object files or libraries may also be included (specified using the flag -lm).

  • The loader is used to load the binary executable file into memory so that it can run on a CPU core.

  • The activity associated with linking and loading is relocation, which assigns final addresses to parts of the program and adjusts the code and data in the program to match these addresses.

To run the loader, simply enter the name of the executable file on the command line. When the program name is typed on the command line (for example, ./main),

  • The shell first creates a new process to run the program via the fork() system call.

  • Then, the shell uses the exec() system call to invoke the loader and passes the name of the executable file to exec().

  • The loader then uses the address space of the newly created process to load the specified program into memory.

So far, we have assumed that all libraries are linked into the executable file and loaded into memory. In reality, most systems allow programs to dynamically link to libraries at load time; for example, Windows supports dynamically linked libraries (DLLs). The advantage of this approach is that it avoids linking and loading libraries that may ultimately go unused into the executable file (thereby reducing extra overhead), because libraries are conditionally linked and loaded only when needed while the program is running. This is possible because the linker inserts relocation information, allowing libraries to be dynamically linked and loaded when the program is loaded.

Object files and executable files usually have a standard format, including compiled machine code, as well as a symbol table containing metadata about functions and variables referenced in the program. For UNIX and Linux systems, this standard format is called ELF (executable and linkable format). There are separate ELF formats for relocatable and executable files. One piece of information in the ELF file of an executable file is the program’s entry point, which contains the address of the first instruction to be executed when the program runs.

2.6 Why Applications Are Operating-System Specific

There are several ways to make an application run on multiple OSes:

  • Write the application in an interpreted language, and the interpreter is available on multiple OSes (such as Python, Ruby).

  • Write the application in a language that includes a virtual machine for running the application (such as Java).

  • Application developers can use standard languages or APIs, and the compiler generates binary code specific to the machine and operating system (such as the POSIX API).

In theory, these methods provide solutions for running applications on different OSes, but implementation is fraught with difficulties, for the following reasons:

At the application level: applications that call certain APIs cannot run on OSes that do not provide those APIs.

At the system level: each OS has a binary format specified for applications, and this format determines the layout of headers, instructions, and variables. These components need to be in specific locations within a specific structure in the executable file so that the operating system can open the file and load the application for correct execution. Both UNIX and Linux have adopted the ELF format as the standard for binary executable files, but this format is not tied to any particular computer architecture, so it cannot guarantee that an executable file will run on different hardware platforms. CPUs have different instruction sets, and only applications containing the appropriate instructions can execute correctly. The system calls provided by different OSes differ in many ways, including the specific operands used and the order of operands, how applications invoke system calls, and so on.

Similar to how APIs specify concrete functions at the application level, at the architecture level there is something called an ABI (application binary interface), which defines how different binary code components interact with a specific OS on a specific architecture.

  • The ABI specifies low-level details, including address width, the method for passing parameters to system calls, the organization of the runtime stack, the binary format of system libraries, and the sizes of data types, among others.

  • So if a binary executable file is compiled and linked according to a specific ABI, it should be able to run on different systems that support that ABI.

  • However, because a specific ABI is defined for a specific operating system running on a given architecture, the ABI has limited usefulness in providing cross-platform compatibility.

2.7 Operating-System Design and Implementation

Mechanisms and Policies

Mechanism: A low-level method or protocol for implementing a functional fragment; it is a low-level kind of “machinery,” such as a context switch.

It provides an answer to the “how” question about a certain system.

Policy: An algorithm for making decisions within an OS; it is a high-level kind of “intelligence,” such as a scheduling policy.

It provides an answer to the “which” question.

By separating mechanism from policy, we can easily change the policy without having to reconsider the mechanism. Therefore, this is a form of modularity and also conforms to a general principle of software design.

Implementation

Early OSes were written in assembly language, while most OSes today are written in high-level languages such as C or C++, with only a few systems written in assembly. The advantages of using high-level languages to implement an OS include:

  • The same benefits gained in application development: code can be written faster, is more compact in structure, and is easier to understand and debug.

  • In addition, advances in compiler technology have improved the quality of code generated for the entire OS (through simple recompilation).

  • Finally, if an OS is written in a high-level language, porting it to other hardware platforms is much easier, which is especially important for an OS that needs to run on many different hardware systems.

The only potential disadvantages of implementing an OS in a high-level language may be reduced execution speed and increased storage requirements. But from today’s perspective, this is not really a problem.

Although assembly language experts can write efficient small routines, for large programs, modern compilers can perform complex analysis and apply sophisticated optimization techniques, thereby generating excellent code.

In addition, modern processors have deep pipelines and multiple functional units, and their ability to handle the details of complex dependencies far exceeds what the human brain can manage.

2.8 Operating-System Structure

A large and complex system must be carefully designed if it is to function properly and be easy to modify. The usual approach is to break the task down into small components or modules rather than building a single monolithic system. Each module should be a clearly defined part of the system, with clearly defined interfaces and functions. The following will explore how the common components of an OS are connected to one another and form a kernel.

Monolithic Structure

The simplest structure for organizing an operating system is no structure at all—that is, placing all kernel functionality into a single, static binary file that runs in a single address space. This approach is known as monolithic structure and is a common technique for designing operating systems.

A typical example is this: the earliest UNIX operating system consisted of two parts: the kernel and system programs. The kernel was further divided into a series of interfaces and device drivers, which were continuously added and expanded over the years as UNIX evolved. We can regard the traditional UNIX operating system as layered to some extent, as shown in the figure below.

Everything below the system call interface and above the physical hardware is the kernel. The kernel provides the file system, CPU scheduling, memory management, and other operating-system functions through system calls. Taken in sum, that is an enormous amount of functionality to be combined into just one single address space.

The Linux operating system is based on UNIX and has a similar structure, as shown in the figure on the right. Applications typically use the glibc standard C library to communicate with the system call interface in order to access the kernel. The Linux kernel is monolithic because it runs entirely in a single address space in kernel mode. But as we will mention later, it also has a modular design that allows it to be modified while the kernel is running.

Although monolithic kernels are simple enough, they are difficult to implement and extend. However, this structure has a significant performance advantage: the overhead of the system call interface is very small, and communication within the kernel is fast. Therefore, despite its various disadvantages, quite a few operating systems still adopt this structure today.

Layered Approach

Monolithic architecture is often referred to as a tightly coupled system, because a change in one part of the system may have widespread effects on other parts. Another option is to design a loosely coupled system. Such a system is divided into independent, small components with specific and limited functionality, all of which together form the kernel. The advantage of a modular approach is that modifications to one component affect only that component itself and do not波及 other parts, thereby giving system implementers greater freedom in creating and changing the internal working mechanisms of the system.

There are many ways to achieve system modularity. One approach is the layered approach, which decomposes the OS into several layers (levels). The lowest layer (Layer 0) is the hardware, and the highest layer (Layer N) is the user interface.

A layer of an OS is an implementation of an abstract object composed of data and the operations that can act on that data. A typical OS layer—for example, Layer M—contains data structures and a set of functions that can be called by higher layers. Correspondingly, Layer M can call operations of lower layers.

The main advantage of the layered approach is that it makes construction and debugging simple: the first layer can be debugged without considering the rest of the system, because by definition it implements functionality using only the underlying hardware (assuming it is correct). Once the first layer has been debugged, the second layer can be debugged on the assumption that it operates correctly, and so on. If an error is found during the debugging of a particular layer, then the error must exist in that layer, because the layers below it have already been debugged. In this way, the design and implementation of the system are simplified, and each layer hides the existence of certain data structures, operations, and hardware from higher layers.

Layered systems have been successfully used in computer networks (such as the TCP/IP protocol) and Web applications. However, relatively few OSs adopt a purely layered approach, for reasons including:

  • It is difficult to properly define the functionality of each layer.

  • User programs need to traverse multiple layers to obtain OS services, which introduces considerable overhead.

Microkernels

The microkernel approach constructs the OS by removing all unnecessary components from the kernel and implementing them as user-level programs placed in separate address spaces. The result is a smaller kernel. There is currently little consensus on which services should remain in the kernel and which should be implemented in user space. However, it is certain that the microkernel provides only the most basic process and memory management functions, as well as communication mechanisms. The main function of a microkernel is to provide communication between client programs and various services that also run in user space. This communication is achieved through message passing. For example, if a client program wants to access a file, it must interact with the file server. Client programs and services never interact directly, but instead communicate indirectly by exchanging messages with the microkernel.

The benefits of adopting the microkernel approach include:

  • It is easier to extend the OS: all new services are added to user space, so there is no need to modify the kernel. When the kernel does need to be modified, because the microkernel itself is small, the required changes are relatively few. The resulting OS is easier to port from one hardware design to another.

  • In addition, because most services run as user processes rather than kernel processes, the microkernel also provides greater security and reliability. Even if a service fails, the rest of the OS is not affected.

However, the performance of a microkernel may suffer because of the increased overhead of system functions. When two user-level services need to communicate, messages must be copied between those services, which are located in different address spaces. In addition, the OS may need to switch between processes to exchange information. Therefore, the overhead caused by message copying and process switching has always been the biggest obstacle hindering the development of microkernel-based OSs.

Modules

The best approach to current OS design is perhaps to use loadable kernel modules (LKMs). In this design, the kernel contains a set of core components and can link additional services through modules at boot time or at runtime. This design pattern is very common in modern UNIX implementations.

The core idea of this design is to have the kernel provide basic services, while other functions are implemented dynamically while the kernel is running. Compared with adding new functionality directly to the kernel, which requires recompiling the kernel for every modification, dynamically linking services is preferable. For example, we can build CPU scheduling and memory management algorithms directly into the kernel, and then add support for different file systems through loadable modules.

The overall architecture is similar to a layered system: each kernel part has a clear and protected interface; but it is more flexible than a layered system because any module can call other modules.

This approach also has similarities with microkernel architecture: the main module contains only core functionality and the mechanisms for loading and communicating with other modules; but it is more efficient because modules do not need to communicate through message passing.

Linux mainly uses LKMs to support device drivers and file systems. LKMs can be “inserted” into the kernel at system boot time or at runtime. If the Linux kernel lacks a required driver, it can be loaded dynamically. At the same time, LKMs can also be removed from the kernel at runtime. For Linux, LKMs achieve a dynamic, modular kernel design while maintaining the performance advantages of a monolithic system.

Hybrid Systems

In practice, few OSs adopt a single, strictly defined structure—they often combine different structures, forming hybrid systems to address performance, security, and usability issues. For example:

Linux is monolithic, because placing the OS within a single address space provides very efficient performance; but at the same time, it is also modular, so that new functionality can be dynamically added to the kernel.

Windows is likewise largely monolithic in structure (also mainly for performance reasons), but it retains some behaviors typical of microkernel systems, including support for independent subsystems that run as user-mode processes. Windows systems also support dynamically loadable kernel modules.

2.9 Building and Booting an Operating System

Operating-System Generation

Steps to generate (or build) an OS from scratch:

  1. Write the operating system source code (or obtain previously written source code)

  2. Configure the target system for the operating system to be run

  3. Compile the operating system

  4. Install the operating system

  5. Boot the computer and its new operating system

System Boot

Most system startup processes proceed as follows:

  1. A piece of code called a bootstrap program or boot loader, used to locate the kernel

  2. The kernel is loaded into memory and started

  3. The kernel initializes the hardware

  4. The root file system is mounted

The boot loader is not part of the operating system!

Some computer systems use a multi-stage boot process:

  1. When the computer is first powered on, a small boot loader located in non-volatile firmware (called BIOS (Basic Input/Output System)) runs

  2. This initial boot loader is usually responsible only for loading a second boot loader, which is located at a fixed position on the hard disk, the so-called boot block

  3. The program stored in the boot block may be complex enough to load the entire OS into memory and begin execution. But more commonly: it is simply code (because it must fit within a single disk block) that knows only the address and length of the remaining boot program on the disk

Many modern computer systems have replaced the BIOS-based boot process with UEFI (unified extensible firmware interface). Compared with BIOS, UEFI has several advantages, including better support for 64-bit systems and larger-capacity hard disks, but the greatest advantage is that it is a standalone and complete boot manager, and therefore faster than the multi-stage BIOS boot.

Whether booting via BIOS or UEFI, the boot program can perform a variety of tasks.

In addition to loading the file containing the kernel program into memory, it also runs diagnostics to detect the machine state, such as checking memory, the CPU, and identifying devices; if the diagnostics pass, the program continues with the subsequent boot steps

The boot program can also initialize various aspects of the system, from CPU registers to device controllers and the contents of main memory

Eventually it starts the operating system and mounts the root file system, and only then do we consider the system to be officially running

To save space and shorten startup time, the Linux kernel image is a compressed file that is decompressed after being loaded into memory. During startup, the boot loader usually creates a temporary RAM file system called initramfs. This file system contains the necessary drivers and kernel modules that must be installed to support the actual root file system (which is not in main memory). Once the kernel starts and the required drivers are installed, the kernel switches the root file system from the temporary RAM location to the appropriate root file system location. Finally, Linux creates the systemd process (the initial process in the system), and then starts other services. Eventually the system will present a login prompt to the user.

2.10 Operating-System Debugging

Broadly speaking, debugging is the activity of finding and fixing errors in a system, including both hardware and software. Performance issues are also regarded as defects, so debugging can also include performance tuning, that is, improving performance by eliminating processing bottlenecks. This section will discuss the debugging process as well as kernel errors and performance issues, but hardware debugging is outside the scope of this article.

Failure Analysis

If a process fails, most operating systems write the error information to log files to alert a system administrator or user that a problem has occurred. The OS may also perform a core dump, capturing the memory contents of the process and storing them in a file for later analysis. A running program and core dumps can be explored by a debugger, allowing a programmer to examine a process’s code and memory in depth when a failure occurs.

Debugging user-level process code is difficult enough, but OS kernel debugging is even more complex because the kernel is large, complex, controls hardware resources, and lacks user-level debugging tools. A failure in the kernel is called a crash. When a crash occurs, error information is saved to a log file, and the memory state is saved to a crash dump file.

Because the nature of the tasks is very different, OS debugging and process debugging often use different tools and techniques. One common technique is to save the kernel’s memory state to a disk area specially reserved for this purpose that contains no file system. If the kernel detects an unrecoverable error, it writes the entire memory contents (or at least the portion of system memory occupied by the kernel) to that disk area. After the system reboots, a process runs to collect the data from that area and write it to a crash dump file located in some file system for analysis. Clearly, for the debugging of ordinary user-level processes, such a strategy is unnecessary.

Performance Monitoring and Tuning

To identify bottlenecks in performance tuning, we must be able to monitor system performance. Therefore, the OS must have methods for computing and displaying metrics of system behavior. Tools can be categorized as providing either per-process or system-wide observation capabilities. To achieve these observations, tools can employ one of two approaches—counters or tracing techniques, and these two approaches are discussed one by one next.

Counters

Tools in Linux that use counters:

Process-level:

  • ps: reports information about a single or selected processes

  • top: reports real-time statistics of current processes (the more modern tool btop is recommended)

System-level:

  • vmstat: reports memory usage statistics

  • netstat: reports statistics of network interfaces

  • iostat: reports disk I/O usage

Most counter-based tools in Linux systems read statistics from the /proc filesystem. It is a “pseudo” filesystem that exists only in kernel memory and is mainly used to query various process-level and kernel statistics. This filesystem is organized in a directory hierarchy, with each process (assigned a unique integer value) appearing as a subdirectory under /proc. For example, the directory entry /proc/2155 will contain the statistics of the process with ID 2155.

Tracing

Tracing tools collect data on specific events, such as the various steps during the execution of a system call. The following are examples of Linux tools used to trace events:

Process level:

  • strace: Traces the system calls invoked by a process

  • gdb: Source-level debugger

System level:

  • perf: A collection of Linux performance tools

  • tcpdump: Collects network packets

Chapter 3 Processes

3.1 Concept

The OS executes various programs. In a batch system, these are called jobs; in a time-sharing system, they are called user programs or tasks. Most modern operating systems are time-sharing systems.

Time sharing: By letting one entity use a resource briefly, then letting another entity use these resources briefly, and repeating this cycle, the same resources are shared among many users.

Space sharing: Resources are allocated (in space) to those who wish to use them. For example, disk space is a space-shared resource—once a block is allocated to a file, it is usually not allocated to another file until the user deletes the original file.

We can simply regard a process as a program in execution; but in reality, a process contains more information and serves as the basic unit of resource allocation.

The current activity state of a process is represented by the value of the program counter and the contents of the processor registers.

The memory layout of a process is divided into multiple sections, including:

  • Text section: executable code

  • Data section: global variables

  • Heap section: memory dynamically allocated while the program is running

  • Stack section: temporary data storage during function calls (such as function parameters, return addresses, local variables, etc.)

It is worth noting that the sizes of the text section and data section are fixed, because their sizes cannot change while the program is running; whereas the sizes of the heap section and stack section can dynamically grow and shrink during program execution. Although the stack section and heap section expand toward each other, the OS ensures that the two do not overlap.

To emphasize again: a program itself is not a process!

A program is merely a passive entity (for example, a file stored on disk containing a list of instructions, that is, an executable file).

In contrast, a process is an active entity, containing a program counter (which indicates the next instruction to be executed) and a set of computing resources.

When an executable file is loaded into memory, the program becomes a process.

Sometimes two or more processes may be associated with the same program, and we must regard them as separate execution sequences, because although the text section is the same, the other sections are all different.

In addition, a process itself can be the execution environment for other code, such as the JVM.

Process State

A process may be in one of the following states:

  • New: the process is being created.

  • Running: instructions are being executed.

  • Waiting: the process is waiting for some event to occur.

  • Ready: the process is waiting to be assigned to a processor for execution.

  • Terminated: the process has finished execution.

The names of the above states can be arbitrary, and different OSs may use different names, but the above states are common to all OSs. It should be noted that a processor core can run only one process at any given time, so many processes will be in the ready or waiting state. The figure below shows the corresponding state diagram. Process Control Block

In an OS, each process is represented by something called a process control block (PCB), also known as a task control block. The PCB contains many pieces of information about a specific process, including:

Process state: including but not limited to the states mentioned earlier

Program counter: indicates the address of the next instruction to be executed for that process

CPU registers:

  • Vary in number and type depending on the CPU architecture

  • Include accumulators, index registers, stack pointers, general-purpose registers, and any status code information

  • When an interrupt occurs, the information in the CPU registers must be saved so that the process can continue execution afterward

CPU-scheduling information: includes process priority, pointers to scheduling queues, and any other scheduling parameters

Memory-management information: includes the values of base and limit registers, page tables or segment tables, and other such items, depending on the memory system used by the OS

Accounting information: includes CPU and real time used, account numbers, job or process numbers, etc.

I/O status information: the list of I/O devices allocated to the process, the list of open files, etc.

Threads

The process model discussed above only considers the case of executing a single thread, but one thread means that a process can only execute one task at the same time. Therefore, most modern OSs have long extended the process concept to allow a process to have multiple threads of execution, thereby enabling it to execute multiple tasks at the same time. This feature is especially useful in multicore systems, because multiple threads can run in parallel.

For an introduction to multithreading, please see the next chapter.

3.2 Process Scheduling

A process scheduler selects a process from a set of available processes and places it on a processor core for execution. However, a CPU can execute only one process at a time. If the number of processes exceeds the number of cores, the extra processes must wait until a core becomes idle before they can be rescheduled. The number of processes currently in memory is called the degree of multiprogramming.

Generally speaking, most processes can be divided into:

I/O-bound process: spends more time on I/O than on computation.

CPU-bound process: generates I/O requests less frequently and spends more time on computation.

Scheduling Queues

When processes enter the system, they are placed in the ready queue. These processes are all in the ready state, waiting to be executed by a CPU core. The queue is stored as a linked list: the head of the queue contains a pointer to the first PCB in the list, and each PCB contains a pointer to the next PCB.

Suppose a process issues an I/O request to a device such as a disk. Since the device runs much more slowly than the processor, the process will have to wait for the I/O to become idle. Therefore, these processes waiting for a specific event to occur will be placed in a wait queue.

Initially, a new process is placed in the ready queue and then waits until it is selected (or dispatched) for execution. Once a process is assigned to a CPU core for execution, one of the following events will occur:

  • The process initiates an I/O request and is then placed in the I/O wait queue.

  • The process creates a new child process and is then placed in the wait queue until the child process terminates.

  • The process may be forcibly removed from the core due to an interrupt or the expiration of its time slice, and is placed back in the ready queue.

CPU Scheduling

A process migrates between the ready queue and various waiting queues during its lifetime. The role of the CPU scheduler is to make a selection among the processes in the ready queue and allocate a CPU core to one of them. It must frequently select a new process for the CPU. Therefore, although a CPU-bound process may take longer to occupy a CPU core, the scheduler will not allocate the core to one process for a long time. More likely, it will force the process to be removed from the CPU and schedule another process to run (that is, preempt it).

Some OSs have an intermediate form of scheduling called swapping. Its general idea is to remove processes from memory (and from active competition for the CPU) to reduce the degree of multiprogramming. The processes can then be reintroduced into memory and can continue execution from where they left off. Swapping is used only in scenarios where memory is overcommitted and must be freed.

Three-level scheduling:

  • High-level / long-term: from the disk buffer pool to memory

  • Medium-level / middle-term: when memory is full, move some out of memory (swap-out), and when memory has space again, swap them back in (swap-in)

  • Low-level / short-term: select a process from the ready queue and allocate the CPU to it

Context Switch

As mentioned earlier, an interrupt causes the OS to switch the CPU core from executing the current task to running a kernel routine, and interrupts occur frequently. When an interrupt occurs, the system needs to save the context information of the process currently executing on the core (state save), so that the suspended process can later be restored and continue executing (state restore). The process’s PCB can represent context information, including CPU registers, process state, and so on.

3.3 Operations on Processes

Process Creation

During execution, a process may create multiple new processes. The process that creates these processes is the parent process, and the newly created processes are the children of that process. They can also create new processes, thus forming a tree. In addition, most operating systems use a unique process identifier (pid) (usually an integer) to identify a process, which can be used as an index to access various kernel process attributes. The figure below shows a typical Linux process tree.

  • The systemd process serves as the root process for all user processes and is the first process at system startup.

  • Once the system starts, the systemd process creates other processes, such as ssh, logind, etc.

  • The logind process is responsible for managing clients that log in directly to the system. After a client logs in, bash is used, and correspondingly such a child process is created.

  • In the bash CLI interface, the user creates ps and vim processes.

  • The sshd process is responsible for managing clients that connect to the system via ssh.

Generally speaking, when a process creates a child process, the child process needs certain resources to complete its task. The child process may obtain these resources directly from the OS, or it may be restricted to using only a subset of the parent process’s resources. The parent process may need to allocate its resources among multiple child processes, or be able to share certain resources with some child processes. Limiting the child process’s resources to a certain range within the parent process’s resources can prevent any situation in which creating too many child processes causes the system to become overloaded.

In addition to providing various physical and logical resources, the parent process may also pass initialization data (input) to the child process.

When a process creates a new process, there are the following two execution possibilities:

  • The parent process and the child process continue to execute concurrently.

  • The parent process waits until some child processes terminate.

A new process also has the following two address space possibilities:

  • The child process is a copy of the parent process (both the program and data are the same as the parent process).

  • The child process corresponds to a newly loaded program.

In UNIX systems, a new process is created through the fork() system call. The new process contains a copy of the original process’s address space. This mechanism makes it easy for the parent process to communicate with its child process. These two processes (the parent process and the child process) continue executing at the instruction after fork(), but with one difference: for the child process, the return code of fork() is 0, while the child process’s pid is returned to the parent process.

For parent and child processes obtained from the same program, we cannot determine which one runs first and which one runs later, because the CPU scheduler adopts different scheduling strategies at different times and under different circumstances. However, if the parent process uses the wait() system call, it will definitely wait for the child process to terminate before continuing to run, so the order in which the two run is then determined.

After the fork() system call, by using the exec() system call, a program different from the currently calling program can be run. Specifically, it loads code (and static data) from the specified executable file and overwrites the contents of the current code segment and static data. In addition, it reinitializes the program’s heap, stack, and other memory spaces.

Process Termination

When a process completes execution of its last statement, the process terminates, and by using the exit() system call, it lets the OS delete it. At this point, the process may return a status value (an integer) to a waiting parent process (through the wait() system call, whose parameter is the child process’s exit status and whose return value is the pid of the terminated child process), and all resources used by the process are released and reclaimed by the OS.

Process termination can also occur in other situations. For example, a process can terminate another process through a system call. Usually, such system calls can only be invoked by the parent process of the process to be terminated; otherwise, users or misbehaving applications could arbitrarily kill other users’ processes. It should be noted that if a parent process wants to terminate its child process, it needs to know the child process’s id. Therefore, when a process creates a new process, the id of the newly created process is passed to the parent process.

The following summarizes some possible reasons why a parent process may terminate a child process (in which case abort() needs to be called):

  • The child process uses more resources than the limit that should have been allocated to it (to determine whether this has occurred, the parent process must have a mechanism to check the child process’s status).

  • The task assigned to the child process no longer needs to be handled.

  • The parent process exits, and the OS does not allow the child process to continue executing after the parent process terminates. This phenomenon is called cascading termination.

When a process terminates, although its resources are immediately reclaimed by the OS, its entry in the process table must be retained until the parent process calls wait(), because that table records the process’s exit status. We call processes that have already terminated but whose parent process has not yet called wait() zombie processes. All processes go through this state when they end, but they usually exist as zombies only briefly. Once the parent process calls wait(), the zombie process’s identifier and its entry in the process table are released.

If the parent process does not call wait() but instead terminates directly, this will cause its child processes to become orphans. The UNIX system’s solution is to designate the init process as the new parent process of these orphan processes. init periodically executes the wait() call, thereby being able to collect the exit status of any orphan process and release the orphan’s pid and its entry in the process table. In Linux, systemd plays the role of init.

3.4 Interprocess Communication

In an OS, concurrently executing processes may be independent processes or cooperating processes.

  • If a process does not share data with any other executing process in the system, then it is independent.

  • A process is cooperating if it can affect or be affected by other executing processes in the system. Any process that shares data with other processes falls into this category.

The reasons for providing an environment that allows processes to cooperate are:

  • Information sharing: because some applications may be interested in the same piece of information, an environment that allows concurrent access to such information must be provided.

  • Computation speedup: if a particular task is to run faster, it must be broken into multiple subtasks, and these subtasks must be executed in parallel. Such speedup can be achieved only when the computer has multiple process cores.

  • Modularity: we may want to build the system in a modular way, for example, by dividing system functions into separate processes or threads.

Cooperating processes require an interprocess communication (IPC) mechanism so that they can exchange data, that is, send and receive data to and from each other. There are two basic interprocess communication models:

  • Shared memory: establish a region of memory shared by cooperating processes, and the processes can then exchange information by reading and writing data to that shared region.

  • Message passing: cooperating processes communicate by exchanging messages.

The figure below shows these two types of communication models:

Both types of models are very common in operating systems, and many systems implement both of them at the same time.

Message passing is useful when exchanging small amounts of data because there is no need to avoid conflicts; moreover, in distributed systems, message passing is easier to implement than shared memory.

Shared memory may be faster than message passing because message passing systems are usually implemented using system calls and therefore require more time-consuming kernel intervention tasks. In a shared memory system, however, system calls are only needed to establish the shared memory region; once shared memory is established, all accesses are treated as regular memory accesses and do not require the kernel’s help.

Shared Memory

IPC using shared memory requires communicating processes to establish a shared memory region, which is usually located within the address space of the process that creates the shared memory segment, while other processes wishing to use this shared memory segment for communication must attach it to their own address spaces.

The OS usually prevents one process from accessing another process’s memory; shared memory requires processes to remove this restriction, after which they can exchange information by reading and writing data in the shared region.

The processes themselves decide the format and location of the data, and must also ensure that simultaneous write operations to the same location are prohibited (not under the OS’s control).

To further explain the concept of cooperating processes, the following introduces the common paradigm of the producer-consumer problem.

The producer process is responsible for generating information, while the consumer process consumes this information.

Application of shared memory in the producer-consumer problem

  • To allow the producer and consumer processes to run concurrently, we must have a buffer of items that the producer can fill and the consumer can empty, located in the shared memory region of the producer and consumer processes.

  • While the consumer is consuming one item, the producer can simultaneously produce another item.

  • Synchronization must be implemented between the producer and consumer to ensure that the consumer does not try to consume an item that has not yet been produced.

  • Two types of buffers:

    • Unbounded buffer: places no practical limit on the size of the buffer; the consumer may need to wait for new items, but the producer can always produce new items.

    • Bounded buffer: assumes a fixed buffer size; in this case, if the buffer is empty, the consumer must wait; if the buffer is full, the producer must wait.

Message Passing

Message passing provides a mechanism that allows processes to communicate and synchronize their operations without sharing the same address space. This mechanism is particularly useful in distributed environments, where communicating processes may reside on different computers connected through a network.

Message passing must provide at least the following two operations: send(message), receive(message).

The size of messages sent by a process can be either fixed or variable. If only fixed-size messages can be sent, the system-level implementation will be relatively simple and straightforward, but this restriction increases the difficulty of programming. Conversely, variable-size messages require a more complex system-level implementation, but programming therefore becomes simpler.

If processes P and Q need to communicate, they must send and receive messages to and from each other: a communication link must exist between them, and this link can be implemented in many ways. What we focus on here is not the physical implementation of the link, but its logical implementation. The following are several ways to logically implement the link and the send() / receive() operations:

  • Direct / indirect communication

  • Synchronous / asynchronous communication

  • Automatic / explicit buffering

Naming

Processes that want to communicate must have a way to refer to each other, and they can use direct or indirect communication.

Direct communication: Every process that wants to communicate must explicitly specify the recipient or sender of the communication.

  • In this case, the send() and receive() primitives are defined as:

    • send(P, message): Send message to P.

    • receive(Q, message): Receive a message from Q.

  • The communication link has the following properties:

    • A connection is automatically established between every pair of processes that want to communicate, and the processes only need to know each other’s identity to communicate.

    • A link is associated with exactly two processes.

    • There is also exactly one link between each pair of processes.

  • The above scheme exhibits symmetry in addressing; that is, both the sending process and the receiving process must specify each other in order to communicate.

  • There is also a variant that uses asymmetric addressing: only the sender specifies the receiver, while the receiver does not need to specify the sender.

    • In this mode, the send() and receive() primitives are defined as follows: send(P, message): Send message to P; receive(id, message): Receive a message from any process, and id is set to the name of the process communicating with it.

  • The disadvantage of the above two schemes is that the resulting procedure definitions have only limited modularity. Changing the identifier of one procedure may require checking all other procedure definitions, and all references to the old identifier must be found so that they can be changed to the new identifier. In general, any hard-coding technique like this (that is, a method in which identifiers must be explicitly declared) is less preferable than the indirect referencing technique introduced next.

Indirect communication: Messages are sent and received through mailboxes or ports.

  • From an abstract perspective, a mailbox can be viewed as an object: processes can deposit messages into it and also remove messages from it.

  • Each mailbox has a unique identifier; for example, POSIX message queues use integer values to identify mailboxes.

  • A process can communicate with other processes through multiple different mailboxes, but two processes can communicate only when they share the same mailbox.

  • The definitions of the send() and receive() primitives are as follows:

    • send(A, message): Send message to mailbox A.

    • receive(A, message): Receive message from mailbox A.

  • A communication link has the following properties:

    • A link is established between a pair of processes only when both processes have a shared mailbox.

    • A link can be associated with more than two processes.

    • There may be multiple different links between each pair of communicating processes, and each link corresponds to one mailbox.

  • Now suppose that processes P1, P2, and P3 all share mailbox A. Process P1 sends a message to A, while at the same time both P2 and P3 execute receive() operations on A. Which process will receive the message sent by P1? This depends on which of the following methods is chosen:

    • A link is allowed to be associated with at most two processes.

    • At most one process is allowed to perform a receive operation at a time.

    • The system may arbitrarily choose which process receives the message (one of P2 or P3, but not both at the same time). The system can define an algorithm to decide which process receives the message (for example, round robin, that is, letting processes take turns receiving messages).

  • A mailbox can belong to a process or can be owned by the OS.

    • If a mailbox is owned by a process (that is, the mailbox is part of the process’s address space). It is necessary to distinguish the owner (which can only receive messages through this mailbox) from users (which can only send messages to this mailbox). Since each mailbox has a unique owner, there is no confusion about which process should receive messages sent to this mailbox. When the process that owns the mailbox terminates, the mailbox also disappears, and afterward any process attempting to send a message to this nonexistent mailbox must be notified: the mailbox no longer exists.

    • A mailbox owned by the OS has its own existence, that is, it is independent and is not attached to any particular process. The OS must provide a mechanism allowing processes to perform the following operations: create a new mailbox (the process that creates the new mailbox is by default the owner of that mailbox), send and receive messages through the mailbox, and delete the mailbox. Initially, the mailbox owner is the only process that can receive messages through this mailbox, but ownership and receive permissions can be passed to other processes through appropriate system calls, although this makes it possible for each mailbox to have multiple receivers.

Synchronization

Interprocess communication is implemented by calling the send() and receive() primitives, and each primitive can be implemented with different design schemes: message passing can be blocking or nonblocking, also known as synchronous and asynchronous.

Blocking send: the sending process is blocked until the message is received by the receiving process or mailbox.

Nonblocking send: the sending process continues operating after sending the message.

Blocking receive: the receiver is blocked until a message is available.

Nonblocking receive: the receiver retrieves either a valid message or a null value.

There can be many different combinations of send() and receive(). When both are blocking, a rendezvous between the sender and receiver is achieved. Moreover, the solution to the producer-consumer problem becomes simple and direct: the producer only needs to call the blocking send() and wait for the message to be delivered to the receiver or mailbox; similarly, the consumer also blocks when calling receive() until a message is available. Buffering

Whether communication is direct or indirect, messages exchanged by communicating processes reside in a temporary queue. In general, such queues can be implemented in the following ways:

  • Zero capacity: The maximum length of the queue is zero, so no messages can be waiting on the link. In this case, the sender must block until the receiver receives the message.

  • Bounded capacity: The queue length is finite, n, so it can hold at most n messages. When a new message is sent, if the queue is not full, the message is placed in the queue (possibly by copying the message contents, or by saving a pointer to the message), and the sender can continue executing without waiting. Because the capacity of the link is finite, if the link is full, the sender must wait until there is available space in the queue.

  • Unbounded capacity: The queue length is infinite. Therefore, any number of messages can wait in it, and the sender never blocks.

The zero-capacity case is sometimes referred to as a message system with no buffering, while the other cases are referred to as systems with automatic buffering.

3.5 Communication in Client-Server Systems

Interprocess communication techniques can also be used for communication in client-server systems. Below, we will discuss two communication strategies in client-server systems: sockets and remote procedure calls (RPC).

Sockets

A socket is an endpoint for communication, and a pair of processes communicating over a network uses a pair of sockets.

A socket is formed by concatenating an IP address and a port number, serving as an identifier.

A client-server architecture is typically adopted: the server waits for connection requests from clients by listening on a specific port; once a request is received, the server accepts the connection from the client socket to complete the connection process.

A server implementing a specific service listens on a well-known port. For example, an SSH server listens on port 22, an FTP server listens on port 21, and a web or HTTP server listens on port 80. All ports below 1024 are considered well-known and are used to implement standard services.

The principles of sockets will be explained below using Java, because compared with C/C++, Java provides an easier-to-use API and a richer library of network utility functions. Java provides 3 different types of sockets:

  • Connection-oriented (TCP) sockets are implemented through the Socket class.

  • Connectionless (UDP) sockets use the DatagramSocket class.

  • The MulticastSocket class is a subclass of the DatagramSocket class, and multicast sockets allow data to be sent to multiple recipients.

Although communication using sockets is widely used and efficient, it is considered a low-level means of communication among distributed processes. One reason is that sockets only allow the exchange of unstructured byte streams between communicating threads, and imposing structure on the data is the responsibility of the client or server application.

Remote Procedure Calls

One of the most common forms of remote service is the RPC paradigm, which was designed to abstract the mechanism of procedure calls between systems connected over a network. In many ways it is similar to the IPC mechanisms introduced earlier, and it is usually built on top of such systems. In this case, however, because we are dealing with an environment in which processes execute on different systems, a message-based communication scheme must be used to provide the remote service.

Unlike IPC messages, the messages exchanged in RPC communication are well structured and are therefore no longer merely data packets. Each message is sent to an RPC daemon listening on a port on the remote system, and each message contains an identifier specifying the function to be executed as well as the arguments passed to that function. The function is then executed as requested, and any output is returned to the requester in another message.

At this point a port is merely a number located at the beginning of a message packet. Typically a system has only one network address, but that address can contain multiple ports to distinguish among the many network services it supports. If a remote process needs a service, it sends a message to the corresponding port.

The semantics of RPC enable a client to invoke a procedure on a remote host as if it were calling a local procedure. The RPC system hides the details required to implement communication by providing a stub on the client side. Typically, each separate remote procedure has a corresponding stub. When a client calls a remote procedure, the RPC system invokes the corresponding stub and passes to it the arguments supplied to the remote procedure. This stub is responsible for locating the port on the server and marshaling the arguments. The stub then uses the message-passing mechanism to send a message to the server. A similar stub on the server side receives this message and executes the procedure on the server. If necessary, any return values are passed back to the client in the same manner.

Argument marshaling solves the problem of differences in data representation between client and server machines. Some systems store the most significant byte first (big-endian), whereas others store the least significant byte first (little-endian). Neither order is superior to the other; the choice is arbitrary in computer architecture. To resolve this difference, many RPC systems define a machine-independent data representation. One such representation is called external data representation (XDR). On the client side, argument marshaling involves converting machine-dependent data into XDR before sending it to the server. On the server side, the XDR data is unmarshaled and converted into the server-dependent representation.

Another key issue concerns the semantics of the call. A local procedure call fails only under extreme circumstances, whereas an RPC may fail, be duplicated, or be executed multiple times because of common network errors. One way to address this problem is to have the OS ensure that messages are executed exactly once rather than at most once.

  • At most once:

    • This can be achieved by attaching a timestamp to each message: the server must keep a record of the timestamps of all processed messages, or keep a sufficiently large history to ensure that duplicate messages can be detected.

    • Incoming messages whose timestamps are already in the history are ignored.

    • In this way, the client can send a message one or more times and ensure that it is executed only once.

  • Exactly once:

    • This requires eliminating the risk that the server may never receive the request.

    • To do this, the server must not only implement the “at most once” protocol described above, but must also acknowledge (ACK) to the client that the RPC call has been received and executed.

    • Such ACK messages are very common in network communication: the client must periodically resend each RPC call until it receives the corresponding ACK.

Another important issue concerns communication between the server and the client. In a standard procedure call, some form of binding occurs at link, load, or execution time, so that the name of the procedure call is replaced by the memory address of the procedure call. The RPC scheme likewise requires similar binding of client and server ports, but how does the client learn the port number on the server? Since the two do not share memory, neither has complete information about the other. There are two common solutions:

  • Binding information can be predetermined - in the form of a fixed port address.

    • At compile time, each RPC call has a fixed port number associated with it.

    • Once the program has been compiled, the server cannot change the port number of the requested service.

  • Binding can be done dynamically through a rendezvous mechanism.

    • Typically, the OS provides a rendezvous (also called a matchmaker) daemon on a fixed RPC port.

    • The client then sends a message to this rendezvous daemon containing the name of the RPC it needs to execute, asking for its port address.

    • After receiving the returned port number, all RPC calls are sent to that port until the process terminates (or the server crashes).

    • Although this approach requires the overhead of an additional initial request, it is more flexible than the first method.

4.1 Overview

A thread is the basic unit of task scheduling and execution, including a thread ID, a program counter (PC), a register set, and stack space. A thread shares the code segment, data segment, and other OS resources of the process with other threads belonging to the same process. We can think of a thread as a lightweight process. A thread looks very much like a separate process, except for one difference: threads can share an address space and therefore can access the same data.

Like a process, a thread also has something called a thread control block (TCB), which is used to store the state, register values, stack information, and so on of each thread in the process. When a context switch occurs, the OS uses the TCB to save and restore context information.

Motivation

The reasons for using threads can be summarized in the following two points:

  • Parallelism: Transforming a single-threaded program into tasks that can execute the same job on multiple CPUs is called parallelization; and having each thread use one CPU is a natural and typical way to achieve parallelization.

  • Avoiding process blocking due to slow I/O: Threads allow I/O operations within a single program to overlap with other activities, similar to multiprogramming across processes.

Although these two points can also be achieved through multiple processes alone, what makes threads unique is that a shared address space makes it easy to share data, whereas processes are better suited for tasks that are logically relatively independent and do not need to share data much.

In addition to applications, the kernels of most OSes are also multithreaded. In Linux systems, the ps -ef command can be used to view the kernel processes currently running in the system, among which the thread kthreadd (pid = 2) is the parent thread of all threads.

Multithreading also has broader applications, including the implementation of various algorithms and data structures, as well as current CPU-intensive problems (data mining, graphics, AI, etc.).

Benefits

Responsiveness:

  • A multithreaded interactive application can keep running even when part of it is blocked or performing a long operation, thereby improving responsiveness to the user.

  • This characteristic is especially useful when designing user interfaces. If it is single-threaded, the application will be unresponsive until the operation is completed; whereas if it is executed in a separate asynchronous thread, the application can remain responsive to the user.

Resource sharing:

  • Processes can only share resources through techniques such as shared memory and message passing, and this must be arranged by the programmer.

  • By default, threads share the memory and resources of the process to which they belong, allowing an application to have several different active threads within the same address space.

Economy:

  • Allocating memory and resources when a process is created is not inexpensive; whereas threads share the resources of the process to which they belong, so the cost of creating and switching threads is lower.

  • Generally speaking, thread creation consumes less time and memory than process creation, and context switching between threads is usually faster than context switching between processes.

Scalability: Multithreading can unleash greater potential on multiprocessor architectures because threads can run in parallel on different processing cores.
