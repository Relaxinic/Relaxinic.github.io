1 Basic Concepts

In multiprogramming, we try to use CPU time efficiently. For example, when a process needs to wait, the OS takes back the CPU usage rights from that process and gives them to another process, and this cycle repeats. Such scheduling operations are a basic and important function in an OS; almost all computer resources need scheduling when they are used. Let us first get to know some basic concepts related to scheduling.

1.1 CPU-I/O Burst Cycle

The success of CPU scheduling depends on a property of processes: process execution consists of a cycle of CPU execution and I/O wait, that is, a process alternates between these two states.

  • Process execution begins with a CPU burst cycle, followed by an I/O burst cycle.

  • This is immediately followed by another CPU burst cycle, and then another I/O burst cycle, and so on.

  • The final CPU burst terminates the process's execution through a system request.

Although the length of CPU burst times varies greatly between different processes and different computers, their frequency curve often resembles that shown in the following figure:

This curve usually appears in exponential or hyperexponential form, including a large number of short CPU bursts and a small number of long CPU bursts.

I/O-bound programs usually have many short CPU bursts.

CPU-bound programs, on the other hand, may have only a few long CPU bursts.

When implementing CPU scheduling algorithms, the above distribution characteristics are crucial.

1.2 CPU Scheduler

Whenever the CPU enters an idle state, the OS, with the help of the CPU scheduler, selects a process from memory (specifically, from the ready queue, which stores records of the relevant process PCBs) and allocates a CPU (core) to execute that process.

It should be noted that the ready queue is not necessarily a FIFO queue; it can also be a priority queue, a tree structure, or simply an unordered linked list. This will be described in detail later in the "Scheduling Algorithms" section.

1.3 Preemptive and Nonpreemptive Scheduling

The CPU needs to make a scheduling decision when one of the following situations occurs: when a process

  1. Running state -> Waiting state

  2. Running state -> Ready state

  3. Waiting state -> Ready state

  4. Terminates

For situations 1 and 4, the only scheduling strategy is: a new process must be selected from the ready queue (if one exists) to execute. But for situations 2 and 3, there can also be other choices. We consider that the scheduling that occurs in situations 1 and 4 is nonpreemptive or cooperative; the opposite of this strategy is preemptive scheduling.

Under non-preemptive scheduling, once the CPU has been allocated to a process, that process keeps occupying the CPU until it releases it by terminating or switching to a waiting state (corresponding to the first and last cases).

In fact, almost all modern OSs use preemptive scheduling algorithms.

When data is shared among multiple processes, preemptive scheduling may lead to race conditions.

  • Consider the case where two processes share data: when one process is in the middle of updating the data, it is preempted so that a second process can run; the second process then tries to read this data, which is in an inconsistent state.

  • This issue will be discussed in detail in the next lecture on "process synchronization."

The preemption mechanism affects kernel design.

  • During the execution of a system call, the kernel may be busy carrying out activities on behalf of a process, and such activities may involve modifying critical kernel data; if the process is preempted during this modification, and the kernel then needs to read or modify the same structure, the result will be a mess.

  • A non-preemptive kernel waits for the system call to complete, or performs a context switch only after the process blocks waiting for an I/O operation to complete.

    • "A context switch caused by a process blocking while waiting for an I/O operation to complete" is a kind of overlap operation that can improve CPU utilization.

    • This approach ensures the simplicity of kernel structures, because the kernel will not preempt a process while kernel data structures are in an inconsistent state.

    • However, for real-time computing, which must ensure that tasks are completed within specified deadlines, this kernel execution model performs poorly.

  • A preemptive kernel, by contrast, requires mechanisms such as mutex locks to prevent race conditions when accessing shared kernel data structures. At present, most modern OSs have fully implemented preemptive processing capability when running in kernel mode.

Because interrupts may occur at any time and the kernel cannot ignore them, code sections affected by interrupts must be protected from concurrent use.

  • The OS needs to accept interrupts at almost any time; otherwise input may be lost or output may be overwritten.

  • To avoid code sections being accessed concurrently by multiple processes, they disable interrupts at entry and re-enable interrupts at exit.

  • However, code sections that disable interrupts are not common and usually contain only a small number of instructions.

1.4 Dispatcher

The dispatcher is a component within the CPU scheduling function, and is the module that hands over control of the CPU core to the process selected by the CPU scheduler. Its functions include:

  • Switching the context from one process to another

  • Switching to user mode

  • Jumping to the appropriate location in the user program to resume execution of that program

The dispatcher should be as fast as possible, because it is invoked on every context switch. The time required for the dispatcher to stop one process and start another is called dispatch latency.

Note the distinction between voluntary and nonvoluntary context switches:

  • A voluntary context switch occurs when a process gives up control of the CPU because a resource it needs is currently unavailable.

  • A nonvoluntary context switch, by contrast, occurs when the CPU is forcibly taken away from a process, such as when its time slice has expired or it is preempted by a higher-priority process.

2 Scheduling Criteria

Different CPU scheduling algorithms have their own characteristics, and choosing a particular algorithm may be more favorable to a certain type of process. Therefore, when selecting which algorithm to use, the characteristics of various algorithms must be considered. There are already multiple criteria for comparing CPU scheduling algorithms, including:

CPU utilization:

  • We want to keep the CPU as busy as possible.

  • Theoretically, CPU utilization can vary from 0% to 100%.

  • In real systems, however, it should usually range from 40% (for lightly loaded systems) to 90% (for heavily loaded systems).

Throughput: the number of processes completed per unit time.

Turnaround time: the time interval from when a process is submitted (arrives) to when it is completed, including the total time the process spends waiting in the ready queue, executing on the CPU, and performing I/O operations.

  • It is a performance metric.

Waiting time: the sum of all waiting periods in the ready queue.

  • CPU scheduling algorithms do not affect the total amount of time a process spends executing or performing I/O operations; they only affect the amount of time a process waits in the ready queue.

  • Waiting time = turnaround time - running time.

Response time: the time from when a request is submitted (arrives) to when the first response is produced.

  • It is often used in interactive systems.

  • Sometimes response time also refers to the time from when a request arrives to when the system first schedules it, which is slightly different from the definition above.

  • It is a fairness metric, that is, on a small time scale, allocating the CPU evenly among active processes.

Ideally, we want to maximize CPU utilization and throughput while minimizing turnaround time, waiting time, and response time.

In most scenarios, what we optimize is the average metric.

However, in certain specific cases, we prefer to optimize the minimum or maximum value rather than the average.

For example, to ensure that all users receive a good service experience, we may want to minimize the maximum response time.

For interactive systems, reducing the variance in response time is more critical than reducing the average response time.

A system with reasonable and predictable response time, even if its average speed is not the fastest but its performance is stable, is usually considered better than systems with fast average speed but large fluctuations.

However, research on CPU scheduling algorithms optimized for reducing variance is still insufficient.

3 Scheduling Algorithms

Currently, only the case of a single available processing core is considered, that is, the case where a CPU can run only one process within a certain time period, while the CPU scheduling problem in multiprocessor systems will be discussed later.

If, when introducing an algorithm, it is not explicitly stated whether it is preemptive, then it can be either preemptive or non-preemptive.

3.1 First-Come, First-Served Scheduling

The simplest CPU scheduling algorithm is the first-come first-served (FCFS) scheduling algorithm.

The first process to request the CPU is allocated the CPU first.

The FCFS policy can be easily implemented with a first-in first-out (FIFO) queue.

When a process enters the ready queue, its PCB is linked to the tail of the queue.

The idle CPU is then allocated to the process at the head of the queue, and that process is subsequently removed from the queue.

Writing and understanding the code for FCFS scheduling is very simple.

However, the disadvantage is that the average waiting time is usually long.

Suppose there is one CPU-bound process and multiple I/O-bound processes. As these processes move through the system, the following situation may occur:

  • The CPU-bound process acquires and occupies the CPU. During this time, all other processes complete their I/O operations and enter the ready queue, waiting to use the CPU, while the I/O devices are idle.

  • Afterward, the CPU-bound process finishes its CPU burst and moves to some I/O device; at this point, those I/O-bound processes with short CPU bursts execute quickly and return to their respective I/O queues, and the CPU then becomes idle.

  • Subsequently, that CPU-bound process returns to the ready queue and uses the CPU again; all the I/O processes again wait in the ready queue for that process to finish.

  • This is the so-called convoy effect: many relatively small resource consumers (processes) line up behind one consumer that occupies a large amount of resources, resulting in very low CPU and device utilization.

Note that the FCFS scheduling algorithm is non-preemptive, so once the CPU has been allocated to a process, that process keeps the CPU until it releases it. Therefore, for interactive systems, the FCFS algorithm performs very poorly.

3.2 Shortest-Job-First Scheduling

The second algorithm to introduce is the shortest-job-first (SJF) scheduling algorithm.

This algorithm associates with each process the length of its next CPU burst.

Therefore, a more accurate name for this scheduling method would be the "shortest-next-CPU-burst" algorithm.

The term SJF is used because everyone says so ...

When the CPU is idle, it is assigned to the process with the shortest next CPU execution cycle.

If two processes have the same next CPU execution cycle, FCFS scheduling is used to determine the order.

The SJF scheduling algorithm has been proven to be optimal, because it provides the minimum average waiting time for a given set of processes. Moving a short process before a long process reduces the waiting time of the short process by an amount greater than the increase in the waiting time of the long process, so the average waiting time is reduced.

Although the SJF algorithm is optimal, it cannot be implemented precisely in practice because we cannot know the length of the next CPU burst in advance. One approach to this problem is to try to approximate SJF scheduling. It is generally believed that the next CPU burst length will be similar to the previous one, so we can choose the process with the shortest estimated processing time to execute.

3.3 Round-Robin Scheduling

The round-robin (RR) scheduling algorithm is similar to FCFS scheduling, but it introduces a preemption mechanism that enables the system to switch between processes. This algorithm defines a very small time interval called a time quantum/slice, whose length is typically 10 to 100 ms.

The CPU scheduler allocates at most 1 time slice to each process.

The time slice size must be a multiple of the timer interrupt period.

The RR scheduling algorithm is said to be preemptive because a process that has not finished executing after more than 1 time slice will be preempted (unable to continue using the CPU core) and placed at the end of the ready queue (still a FIFO queue) (unless it is the only runnable process at the moment), and then the CPU scheduler selects the first process from the ready queue to execute. Specifically:

Process CPU burst period <= 1 time slice: the process voluntarily releases the CPU, and then the scheduler selects the next process in the ready queue.

Process CPU burst period > 1 time slice: the timer will trigger and send an interrupt signal to the OS; at this point a context switch is performed, and the process is moved to the end of the ready queue; then the CPU scheduler selects the next process in the ready queue to continue execution.

It is not difficult to see that the average waiting time under the RR policy is usually very long.

The performance of the RR algorithm depends to a large extent on the size of the time slice:

  • If the time slice is very large, then the RR policy ≈ the FCFS policy, so responsiveness is poor.

  • If the time slice is very small, a large amount of context-switching overhead will be introduced.

Context-switching overhead includes: saving and restoring register values, handling the state of hardware such as the CPU cache, TLB, and branch predictor.

Therefore, we want the time slice to be sufficiently large relative to the context-switching time; in practice, the time slice range of most modern OSs is between 10-100 ms, while the time required for one context switch is usually < 10 μs, so there is no need to worry about this issue.

Using turnaround time (submission -> completion) as the metric, the RR algorithm is the worst among the three algorithms already introduced, because after using the RR algorithm, the completion time of each process is pushed back, which obviously increases the turnaround time.

In fact, all algorithms that emphasize fairness like RR perform poorly in terms of turnaround time. This reflects a trade-off:

  • If unfairness is allowed, then the shortest process can be allowed to finish running first, at the cost of harming response time.

  • If fairness is emphasized, response time is reduced, but at the cost of harming turnaround time.

So response time and turnaround time are (seemingly) in a relationship where "you cannot have your cake and eat it too."

3.4 Priority Scheduling

The SJF algorithm introduced earlier is a special case of priority-scheduling algorithms (priority = the reciprocal of the next CPU burst).

  • Each process is associated with a priority, and the CPU is allocated to the process with the highest priority.

  • Processes with equal priority are scheduled in FCFS order.

  • Priorities are generally represented by a fixed range of numbers.

  • However, there is still no consensus on whether 0 is the highest or the lowest priority; from now on, we will assume that small numbers represent high priority.

The definition of priority can come from internal or external sources.

  • Internal priority: The priority of a process is calculated using some measurable quantity, for example: time limits, memory requirements, the number of open files, the ratio of average I/O burst to average CPU burst, etc.

  • External priority: Set by criteria external to the OS, such as the importance of the process, the type and amount of money paid for computer use, the department funding the work, and other often political factors.

The main problem with priority scheduling algorithms is indefinite blocking, also known as starvation: numerous high-priority processes consume the CPU, while low-priority processes can only wait and may even never get to use the CPU.

One way to solve this problem is aging (also called priority boost), which periodically increases the priority of processes that have been waiting in the system for a long time (a variant is to boost all processes to the highest priority). However, the aging period needs to be decided by the OS administrator and must be set reasonably.

3.5 Multilevel Queue Scheduling

In the priority + RR scheduling algorithm, all processes are placed in a single queue, so a search of O(n)O(n)O(n) is required to find the process with the highest priority. In practice, it is often easier to set up separate queues for different priorities; in this case, processes only need to be scheduled using the priority scheduling algorithm within the highest-priority queue. This approach is called a multilevel queue.

This method can still be combined with RR scheduling: if there are multiple processes in the highest-priority queue, they will be executed in RR order.

The multilevel queue scheduling algorithm can also divide processes into multiple independent queues based on process type, where each queue has absolute priority over lower-priority queues, as shown in the figure below:

A common division is to separate foreground (interactive) processes from background (batch) processes.

  • Because these two types of processes have different response time requirements, they may need different scheduling policies.

  • Foreground processes may have higher priority than background processes (externally defined).

  • Queues can be set up separately for foreground and background processes, and each queue can use a different scheduling algorithm; for example, the foreground queue may use RR scheduling, while the background queue uses FCFS scheduling.

In addition, scheduling must be performed between queues, generally implemented through preemptive scheduling with fixed priorities.

Another approach is to use an RR-like method between queues: each queue receives a certain proportion of CPU time, which can then be scheduled among its various processes. For example, in the foreground-background queue example, the foreground queue can allocate 80% of the CPU time to its processes for RR scheduling, while the background queue receives 20% of the CPU time, allocated to its processes in FCFS order.

3.6 Multilevel Feedback Queue Scheduling

Generally speaking, when a multilevel queue scheduling algorithm is used, once a process enters the system, it is permanently assigned to a certain queue. The advantage of this setup is low scheduling overhead, but it lacks flexibility.

In contrast, the multilevel feedback queue scheduling algorithm allows processes to move between different queues.

Its core idea is to classify processes based on the characteristics of their CPU execution time: if a process occupies too much CPU time, it will be moved to a lower-priority queue.

In this way, I/O-bound and interactive processes, which are usually characterized by short CPU execution, can remain in higher-priority queues.

In addition, processes that have waited too long in low-priority queues may also be promoted to higher-priority queues. This aging mechanism effectively prevents starvation.

The multilevel feedback queue scheduler is defined by the following parameters:

  • The number of queues

  • The scheduling algorithm for each queue

  • The method used to determine when to promote a process to a higher-priority queue

  • The method used to determine when to demote a process to a lower-priority queue

  • The method used to determine which queue a process enters when it needs service

The multilevel feedback queue scheduler is the most general CPU scheduling algorithm and can simultaneously minimize turnaround time and response time. However, this also makes it the most complex algorithm.

4 Thread Scheduling

This section will discuss the scheduling issues of user-level and kernel-level threads, and provide specific examples for Pthreads scheduling.

4.1 Contention Scope

One difference between user-level threads and kernel-level threads lies in how they are scheduled.

In systems implementing the many-to-one and many-to-many models, the thread library schedules user-level threads to run on available lightweight processes (LWPs), a mechanism known as process-contention scope (PCS), because CPU contention occurs among threads belonging to the same process.

Typically, PCS is based on priority: the scheduler selects the runnable thread with the highest priority to run. This priority is set by the programmer and is not adjusted by the thread library, although some thread libraries may allow the programmer to change a thread's priority.

It should be noted that PCS typically preempts the currently running thread to run a higher-priority thread, but among threads of equal priority, there is no guarantee of time-slice allocation.

To decide which kernel-level thread is scheduled onto the CPU, the kernel uses system-contention scope (SCS). Under this scheduling, all threads in the system compete for the CPU. Systems using the one-to-one model use only SCS to schedule threads.

4.2 Pthread Scheduling

Pthreads defines the following contention scope values:

  • PTHREAD_SCOPE_PROCESS: use PCS-scheduled threads

  • PTHREAD_SCOPE_SYSTEM: use SCS-scheduled threads

In systems using the many-to-many model,

  • The PTHREAD_SCOPE_PROCESS policy schedules user-level threads onto available LWPs; their number is maintained by the thread library and may use scheduling activation

  • The PTHREAD_SCOPE_SYSTEM scheduling policy creates and binds one LWP for each user-level thread, effectively mapping threads using a one-to-one policy

Pthread IPC (interprocess communication) provides two functions for setting and getting the contention scope policy:

  • pthread_attr_setscope(pthread_attr_t *attr, int scope)

  • pthread_attr_getscope(pthread_attr_t *attr, int *scope)

The first parameter of both functions contains a pointer to a thread attributes set. As for the second parameter,

  • pthread_attr_setscope() is passed the value PTHREAD_SCOPE_SYSTEM or PTHREAD_SCOPE_PROCESS to indicate the contention scope

  • pthread_attr_getscope() is passed a pointer to an integer value, which is set to the value of the current contention scope

If an error occurs, these functions return a nonzero value.

5 Multi-Processor Scheduling

The current discussion mainly focuses on how to schedule CPUs on a single-core processor system. When a system has multiple CPUs, load sharing can be achieved, allowing multiple threads to run in parallel, but at the same time the scheduling problem becomes correspondingly more complex. Extensive practice has shown that no optimal scheduling algorithm exists in this case.

Traditionally, the term "multiprocessor" referred to systems equipped with multiple physical processors, each containing a single-core CPU. However, the definition of "multiprocessor" has evolved significantly, and in modern computing systems it refers to system architectures including the following:

  • Multicore CPUs

  • Multithreaded cores

  • NUMA systems

  • Heterogeneous multiprocessing

Next, we will first focus on functionally identical, that is, homogeneous, processor systems, which means that any available CPU can be used to run any process in the queue. Finally, we will discuss the case of systems with differing processor capabilities.

5.1 Approaches to Multiple-Processor Scheduling

In a multiprocessor system, one CPU scheduling approach is to assign all scheduling decisions, I/O processing, and other system activities to a single processor—the master server; the remaining processors execute only user code. This asymmetric multiprocessing approach is relatively simple, because only one core accesses system data structures, thereby reducing the need for data sharing. However, the drawback of this approach is that the master server may become a bottleneck, causing overall system performance to degrade.

The standard practice for supporting multiprocessors is symmetric multiprocessing (SMP), in which each processor can self-schedule. In this case, there are two strategies for organizing schedulable threads:

All threads are placed in one common ready queue (left figure)

  • Race conditions may exist on the common ready queue, so it must be ensured that two independent processors do not schedule the same thread at the same time, and that threads are not lost from the queue.

  • Some form of lock can be used to protect the common ready queue, but doing so shifts contention to the lock, because all accesses to the queue require ownership of the lock, and thus access to the shared queue may become a performance bottleneck.

Each processor has its own private thread queue (right figure)

  • It does not encounter the performance problems associated with a shared run queue, so this is the most common approach in systems that support SMP.

  • This design can use caches more effectively.

  • The biggest problem is differences in workload, but load balancing algorithms can balance the load across all processors.

5.2 Multicore Processors

Most modern computer hardware integrates multiple computing cores onto a single physical chip, forming a multicore processor. Each core maintains its own architectural state, so to the OS they appear as independent logical CPUs. SMP systems using multicore processors are faster and more energy-efficient than systems in which each CPU has its own separate physical chip.

Multicore processors can complicate scheduling. When a processor accesses memory, it spends a considerable amount of time waiting for the data to become ready, a phenomenon known as a memory stall, as shown in the figure below. The reason is that modern processors operate much faster than memory; in addition, cache misses (i.e., the accessed data is not in the cache) can also cause memory stalls.

To address this situation, many recent hardware designs use multithreaded processing cores, with each core assigned two (or more) hardware threads. In this way, if a hardware thread stalls while waiting for memory, the core can switch to another thread.
