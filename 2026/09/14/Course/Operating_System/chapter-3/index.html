1 Concept

The OS executes various programs. In a batch system, these are called jobs; in a time-sharing system, they are called user programs or tasks. Most modern operating systems are time-sharing systems.

Time sharing: By letting one entity use a resource briefly, then letting another entity use these resources briefly, and repeating this cycle, the same resources are shared among many users.

Space sharing: Resources are allocated (in space) to those who wish to use them. For example, disk space is a space-shared resource—once a block is allocated to a file, it is usually not allocated to another file until the user deletes the original file.

We can simply regard a process as a program in execution; but in reality, a process contains more information and serves as the basic unit of resource allocation.

The current activity state of a process is represented by the value of the program counter and the contents of the processor registers.

The memory layout of a process is divided into multiple sections, including:

  • Text section: executable code

  • Data section: global variables

  • Heap section: memory dynamically allocated while the program is running

  • Stack section: temporary data storage during function calls (such as function parameters, return addresses, local variables, etc.)

It is worth noting that the sizes of the text section and data section are fixed, because their sizes cannot change while the program is running; whereas the sizes of the heap section and stack section can dynamically grow and shrink during program execution. Although the stack section and heap section expand toward each other, the OS ensures that the two do not overlap.

To emphasize again: a program itself is not a process!

A program is merely a passive entity (for example, a file stored on disk containing a list of instructions, that is, an executable file).

In contrast, a process is an active entity, containing a program counter (which indicates the next instruction to be executed) and a set of computing resources.

When an executable file is loaded into memory, the program becomes a process.

Sometimes two or more processes may be associated with the same program, and we must regard them as separate execution sequences, because although the text section is the same, the other sections are all different.

In addition, a process itself can be the execution environment for other code, such as the JVM.

1.1 Process State

A process may be in one of the following states:

  • New: the process is being created.

  • Running: instructions are being executed.

  • Waiting: the process is waiting for some event to occur.

  • Ready: the process is waiting to be assigned to a processor for execution.

  • Terminated: the process has finished execution.

The names of the above states can be arbitrary, and different OSs may use different names, but the above states are common to all OSs. It should be noted that a processor core can run only one process at any given time, so many processes will be in the ready or waiting state. The figure below shows the corresponding state diagram. 1.2 Process Control Block

In an OS, each process is represented by something called a process control block (PCB), also known as a task control block. The PCB contains many pieces of information about a specific process, including:

Process state: including but not limited to the states mentioned earlier

Program counter: indicates the address of the next instruction to be executed for that process

CPU registers:

  • Vary in number and type depending on the CPU architecture

  • Include accumulators, index registers, stack pointers, general-purpose registers, and any status code information

  • When an interrupt occurs, the information in the CPU registers must be saved so that the process can continue execution afterward

CPU-scheduling information: includes process priority, pointers to scheduling queues, and any other scheduling parameters

Memory-management information: includes the values of base and limit registers, page tables or segment tables, and other such items, depending on the memory system used by the OS

Accounting information: includes CPU and real time used, account numbers, job or process numbers, etc.

I/O status information: the list of I/O devices allocated to the process, the list of open files, etc.

1.3 Threads

The process model discussed above only considers the case of executing a single thread, but one thread means that a process can only execute one task at the same time. Therefore, most modern OSs have long extended the process concept to allow a process to have multiple threads of execution, thereby enabling it to execute multiple tasks at the same time. This feature is especially useful in multicore systems, because multiple threads can run in parallel.

For an introduction to multithreading, please see the next chapter.

2 Process Scheduling

A process scheduler selects a process from a set of available processes and places it on a processor core for execution. However, a CPU can execute only one process at a time. If the number of processes exceeds the number of cores, the extra processes must wait until a core becomes idle before they can be rescheduled. The number of processes currently in memory is called the degree of multiprogramming.

Generally speaking, most processes can be divided into:

I/O-bound process: spends more time on I/O than on computation.

CPU-bound process: generates I/O requests less frequently and spends more time on computation.

2.1 Scheduling Queues

When processes enter the system, they are placed in the ready queue. These processes are all in the ready state, waiting to be executed by a CPU core. The queue is stored as a linked list: the head of the queue contains a pointer to the first PCB in the list, and each PCB contains a pointer to the next PCB.

Suppose a process issues an I/O request to a device such as a disk. Since the device runs much more slowly than the processor, the process will have to wait for the I/O to become idle. Therefore, these processes waiting for a specific event to occur will be placed in a wait queue.

Initially, a new process is placed in the ready queue and then waits until it is selected (or dispatched) for execution. Once a process is assigned to a CPU core for execution, one of the following events will occur:

  • The process initiates an I/O request and is then placed in the I/O wait queue.

  • The process creates a new child process and is then placed in the wait queue until the child process terminates.

  • The process may be forcibly removed from the core due to an interrupt or the expiration of its time slice, and is placed back in the ready queue.

2.2 CPU Scheduling

A process migrates between the ready queue and various waiting queues during its lifetime. The role of the CPU scheduler is to make a selection among the processes in the ready queue and allocate a CPU core to one of them. It must frequently select a new process for the CPU. Therefore, although a CPU-bound process may take longer to occupy a CPU core, the scheduler will not allocate the core to one process for a long time. More likely, it will force the process to be removed from the CPU and schedule another process to run (that is, preempt it).

Some OSs have an intermediate form of scheduling called swapping. Its general idea is to remove processes from memory (and from active competition for the CPU) to reduce the degree of multiprogramming. The processes can then be reintroduced into memory and can continue execution from where they left off. Swapping is used only in scenarios where memory is overcommitted and must be freed.

Three-level scheduling:

  • High-level / long-term: from the disk buffer pool to memory

  • Medium-level / middle-term: when memory is full, move some out of memory (swap-out), and when memory has space again, swap them back in (swap-in)

  • Low-level / short-term: select a process from the ready queue and allocate the CPU to it

2.3 Context Switch

As mentioned earlier, an interrupt causes the OS to switch the CPU core from executing the current task to running a kernel routine, and interrupts occur frequently. When an interrupt occurs, the system needs to save the context information of the process currently executing on the core (state save), so that the suspended process can later be restored and continue executing (state restore). The process's PCB can represent context information, including CPU registers, process state, and so on.

3 Operations on Processes

3.1 Process Creation

During execution, a process may create multiple new processes. The process that creates these processes is the parent process, and the newly created processes are the children of that process. They can also create new processes, thus forming a tree. In addition, most operating systems use a unique process identifier (pid) (usually an integer) to identify a process, which can be used as an index to access various kernel process attributes. The figure below shows a typical Linux process tree.

  • The systemd process serves as the root process for all user processes and is the first process at system startup.

  • Once the system starts, the systemd process creates other processes, such as ssh, logind, etc.

  • The logind process is responsible for managing clients that log in directly to the system. After a client logs in, bash is used, and correspondingly such a child process is created.

  • In the bash CLI interface, the user creates ps and vim processes.

  • The sshd process is responsible for managing clients that connect to the system via ssh.

Generally speaking, when a process creates a child process, the child process needs certain resources to complete its task. The child process may obtain these resources directly from the OS, or it may be restricted to using only a subset of the parent process's resources. The parent process may need to allocate its resources among multiple child processes, or be able to share certain resources with some child processes. Limiting the child process's resources to a certain range within the parent process's resources can prevent any situation in which creating too many child processes causes the system to become overloaded.

In addition to providing various physical and logical resources, the parent process may also pass initialization data (input) to the child process.

When a process creates a new process, there are the following two execution possibilities:

  • The parent process and the child process continue to execute concurrently.

  • The parent process waits until some child processes terminate.

A new process also has the following two address space possibilities:

  • The child process is a copy of the parent process (both the program and data are the same as the parent process).

  • The child process corresponds to a newly loaded program.

In UNIX systems, a new process is created through the fork() system call. The new process contains a copy of the original process's address space. This mechanism makes it easy for the parent process to communicate with its child process. These two processes (the parent process and the child process) continue executing at the instruction after fork(), but with one difference: for the child process, the return code of fork() is 0, while the child process's pid is returned to the parent process.

For parent and child processes obtained from the same program, we cannot determine which one runs first and which one runs later, because the CPU scheduler adopts different scheduling strategies at different times and under different circumstances. However, if the parent process uses the wait() system call, it will definitely wait for the child process to terminate before continuing to run, so the order in which the two run is then determined.

After the fork() system call, by using the exec() system call, a program different from the currently calling program can be run. Specifically, it loads code (and static data) from the specified executable file and overwrites the contents of the current code segment and static data. In addition, it reinitializes the program's heap, stack, and other memory spaces.

3.2 Process Termination

When a process completes execution of its last statement, the process terminates, and by using the exit() system call, it lets the OS delete it. At this point, the process may return a status value (an integer) to a waiting parent process (through the wait() system call, whose parameter is the child process's exit status and whose return value is the pid of the terminated child process), and all resources used by the process are released and reclaimed by the OS.

Process termination can also occur in other situations. For example, a process can terminate another process through a system call. Usually, such system calls can only be invoked by the parent process of the process to be terminated; otherwise, users or misbehaving applications could arbitrarily kill other users' processes. It should be noted that if a parent process wants to terminate its child process, it needs to know the child process's id. Therefore, when a process creates a new process, the id of the newly created process is passed to the parent process.

The following summarizes some possible reasons why a parent process may terminate a child process (in which case abort() needs to be called):

  • The child process uses more resources than the limit that should have been allocated to it (to determine whether this has occurred, the parent process must have a mechanism to check the child process's status).

  • The task assigned to the child process no longer needs to be handled.

  • The parent process exits, and the OS does not allow the child process to continue executing after the parent process terminates. This phenomenon is called cascading termination.

When a process terminates, although its resources are immediately reclaimed by the OS, its entry in the process table must be retained until the parent process calls wait(), because that table records the process's exit status. We call processes that have already terminated but whose parent process has not yet called wait() zombie processes. All processes go through this state when they end, but they usually exist as zombies only briefly. Once the parent process calls wait(), the zombie process's identifier and its entry in the process table are released.

If the parent process does not call wait() but instead terminates directly, this will cause its child processes to become orphans. The UNIX system's solution is to designate the init process as the new parent process of these orphan processes. init periodically executes the wait() call, thereby being able to collect the exit status of any orphan process and release the orphan's pid and its entry in the process table. In Linux, systemd plays the role of init.

4 Interprocess Communication

In an OS, concurrently executing processes may be independent processes or cooperating processes.

  • If a process does not share data with any other executing process in the system, then it is independent.

  • A process is cooperating if it can affect or be affected by other executing processes in the system. Any process that shares data with other processes falls into this category.

The reasons for providing an environment that allows processes to cooperate are:

  • Information sharing: because some applications may be interested in the same piece of information, an environment that allows concurrent access to such information must be provided.

  • Computation speedup: if a particular task is to run faster, it must be broken into multiple subtasks, and these subtasks must be executed in parallel. Such speedup can be achieved only when the computer has multiple process cores.

  • Modularity: we may want to build the system in a modular way, for example, by dividing system functions into separate processes or threads.

Cooperating processes require an interprocess communication (IPC) mechanism so that they can exchange data, that is, send and receive data to and from each other. There are two basic interprocess communication models:

  • Shared memory: establish a region of memory shared by cooperating processes, and the processes can then exchange information by reading and writing data to that shared region.

  • Message passing: cooperating processes communicate by exchanging messages.

Both types of models are very common in operating systems, and many systems implement both of them at the same time.

Message passing is useful when exchanging small amounts of data because there is no need to avoid conflicts; moreover, in distributed systems, message passing is easier to implement than shared memory.

Shared memory may be faster than message passing because message passing systems are usually implemented using system calls and therefore require more time-consuming kernel intervention tasks. In a shared memory system, however, system calls are only needed to establish the shared memory region; once shared memory is established, all accesses are treated as regular memory accesses and do not require the kernel's help.

4.1 Shared Memory

IPC using shared memory requires communicating processes to establish a shared memory region, which is usually located within the address space of the process that creates the shared memory segment, while other processes wishing to use this shared memory segment for communication must attach it to their own address spaces.

The OS usually prevents one process from accessing another process's memory; shared memory requires processes to remove this restriction, after which they can exchange information by reading and writing data in the shared region.

The processes themselves decide the format and location of the data, and must also ensure that simultaneous write operations to the same location are prohibited (not under the OS's control).

To further explain the concept of cooperating processes, the following introduces the common paradigm of the producer-consumer problem.

The producer process is responsible for generating information, while the consumer process consumes this information.

Application of shared memory in the producer-consumer problem

  • To allow the producer and consumer processes to run concurrently, we must have a buffer of items that the producer can fill and the consumer can empty, located in the shared memory region of the producer and consumer processes.

  • While the consumer is consuming one item, the producer can simultaneously produce another item.

  • Synchronization must be implemented between the producer and consumer to ensure that the consumer does not try to consume an item that has not yet been produced.

  • Two types of buffers:

    • Unbounded buffer: places no practical limit on the size of the buffer; the consumer may need to wait for new items, but the producer can always produce new items.

    • Bounded buffer: assumes a fixed buffer size; in this case, if the buffer is empty, the consumer must wait; if the buffer is full, the producer must wait.

The following variables are located in the memory region shared by the producer and consumer processes:

#define BUFFER_SIZE 10
typedef struct {
    ...
} item;

item buffer[BUFFER_SIZE];
int in = 0;
int out = 0;

It can be seen that the shared buffer is implemented as a circular array with two logical pointers, in and out. The variable in points to the next free position in the buffer; out points to the first occupied position in the buffer. When in == out, the buffer is empty; when ((in + 1) % BUFFER_SIZE) == out, the buffer is full.

The following two pieces of code show the producer process and the consumer process, respectively:

// PRODUCER
item next_produced;

while (true) {
    /* produce an item in next produced */
    while (((in + 1) % BUFFER_SIZE) == out)
        ; /* do nothing */
    buffer[in] = next_produced;
    in = (in + 1) % BUFFER_SIZE;
}

// CONSUMER
item next_consumed;

while (true) {
    while (in == out)
        ; /* do nothing */
    next_consumed = buffer[out];
    out = (out + 1) % BUFFER_SIZE;
    /* consume the item in next consumed */
}

4.2 Message Passing

Message passing provides a mechanism that allows processes to communicate and synchronize their operations without sharing the same address space. This mechanism is particularly useful in distributed environments, where communicating processes may reside on different computers connected through a network.

Message passing must provide at least the following two operations: send(message), receive(message).

The size of messages sent by a process can be either fixed or variable. If only fixed-size messages can be sent, the system-level implementation will be relatively simple and straightforward, but this restriction increases the difficulty of programming. Conversely, variable-size messages require a more complex system-level implementation, but programming therefore becomes simpler.

If processes P and Q need to communicate, they must send and receive messages to and from each other: a communication link must exist between them, and this link can be implemented in many ways. What we focus on here is not the physical implementation of the link, but its logical implementation. The following are several ways to logically implement the link and the send() / receive() operations:

  • Direct / indirect communication

  • Synchronous / asynchronous communication

  • Automatic / explicit buffering

Naming

Processes that want to communicate must have a way to refer to each other, and they can use direct or indirect communication.

Direct communication: Every process that wants to communicate must explicitly specify the recipient or sender of the communication.

  • In this case, the send() and receive() primitives are defined as:

    • send(P, message): Send message to P.

    • receive(Q, message): Receive a message from Q.

  • The communication link has the following properties:

    • A connection is automatically established between every pair of processes that want to communicate, and the processes only need to know each other's identity to communicate.

    • A link is associated with exactly two processes.

    • There is also exactly one link between each pair of processes.

  • The above scheme exhibits symmetry in addressing; that is, both the sending process and the receiving process must specify each other in order to communicate.

  • There is also a variant that uses asymmetric addressing: only the sender specifies the receiver, while the receiver does not need to specify the sender.

    • In this mode, the send() and receive() primitives are defined as follows: send(P, message): Send message to P; receive(id, message): Receive a message from any process, and id is set to the name of the process communicating with it.

  • The disadvantage of the above two schemes is that the resulting procedure definitions have only limited modularity. Changing the identifier of one procedure may require checking all other procedure definitions, and all references to the old identifier must be found so that they can be changed to the new identifier. In general, any hard-coding technique like this (that is, a method in which identifiers must be explicitly declared) is less preferable than the indirect referencing technique introduced next.

Indirect communication: Messages are sent and received through mailboxes or ports.

  • From an abstract perspective, a mailbox can be viewed as an object: processes can deposit messages into it and also remove messages from it.

  • Each mailbox has a unique identifier; for example, POSIX message queues use integer values to identify mailboxes.

  • A process can communicate with other processes through multiple different mailboxes, but two processes can communicate only when they share the same mailbox.

  • The definitions of the send() and receive() primitives are as follows:

    • send(A, message): Send message to mailbox A.

    • receive(A, message): Receive message from mailbox A.

  • A communication link has the following properties:

    • A link is established between a pair of processes only when both processes have a shared mailbox.

    • A link can be associated with more than two processes.

    • There may be multiple different links between each pair of communicating processes, and each link corresponds to one mailbox.

  • Now suppose that processes P1, P2, and P3 all share mailbox A. Process P1 sends a message to A, while at the same time both P2 and P3 execute receive() operations on A. Which process will receive the message sent by P1? This depends on which of the following methods is chosen:

    • A link is allowed to be associated with at most two processes.

    • At most one process is allowed to perform a receive operation at a time.

    • The system may arbitrarily choose which process receives the message (one of P2 or P3, but not both at the same time). The system can define an algorithm to decide which process receives the message (for example, round robin, that is, letting processes take turns receiving messages).

  • A mailbox can belong to a process or can be owned by the OS.

    • If a mailbox is owned by a process (that is, the mailbox is part of the process's address space). It is necessary to distinguish the owner (which can only receive messages through this mailbox) from users (which can only send messages to this mailbox). Since each mailbox has a unique owner, there is no confusion about which process should receive messages sent to this mailbox. When the process that owns the mailbox terminates, the mailbox also disappears, and afterward any process attempting to send a message to this nonexistent mailbox must be notified: the mailbox no longer exists.

    • A mailbox owned by the OS has its own existence, that is, it is independent and is not attached to any particular process. The OS must provide a mechanism allowing processes to perform the following operations: create a new mailbox (the process that creates the new mailbox is by default the owner of that mailbox), send and receive messages through the mailbox, and delete the mailbox. Initially, the mailbox owner is the only process that can receive messages through this mailbox, but ownership and receive permissions can be passed to other processes through appropriate system calls, although this makes it possible for each mailbox to have multiple receivers.

Synchronization

Interprocess communication is implemented by calling the send() and receive() primitives, and each primitive can be implemented with different design schemes: message passing can be blocking or nonblocking, also known as synchronous and asynchronous.

Blocking send: the sending process is blocked until the message is received by the receiving process or mailbox.

Nonblocking send: the sending process continues operating after sending the message.

Blocking receive: the receiver is blocked until a message is available.

Nonblocking receive: the receiver retrieves either a valid message or a null value.

There can be many different combinations of send() and receive(). When both are blocking, a rendezvous between the sender and receiver is achieved. Moreover, the solution to the producer-consumer problem becomes simple and direct: the producer only needs to call the blocking send() and wait for the message to be delivered to the receiver or mailbox; similarly, the consumer also blocks when calling receive() until a message is available. The relevant code for these two types of processes is shown below:

// PRODUCER
message next_produced;

while (true) {
    /* produce an item in next produced */
    send(next_produced);
}

// CONSUMER
message next_consumed;

while (true) {
    receive(next_consumed);
    /* consume the item in next consumed */
}

Buffering

Whether communication is direct or indirect, messages exchanged by communicating processes reside in a temporary queue. In general, such queues can be implemented in the following ways:

  • Zero capacity: The maximum length of the queue is zero, so no messages can be waiting on the link. In this case, the sender must block until the receiver receives the message.

  • Bounded capacity: The queue length is finite, n, so it can hold at most n messages. When a new message is sent, if the queue is not full, the message is placed in the queue (possibly by copying the message contents, or by saving a pointer to the message), and the sender can continue executing without waiting. Because the capacity of the link is finite, if the link is full, the sender must wait until there is available space in the queue.

  • Unbounded capacity: The queue length is infinite. Therefore, any number of messages can wait in it, and the sender never blocks.

The zero-capacity case is sometimes referred to as a message system with no buffering, while the other cases are referred to as systems with automatic buffering.

5 Communication in Client-Server Systems

Interprocess communication techniques can also be used for communication in client-server systems. Below, we will discuss two communication strategies in client-server systems: sockets and remote procedure calls (RPC).

5.1 Sockets

A socket is an endpoint for communication, and a pair of processes communicating over a network uses a pair of sockets.

A socket is formed by concatenating an IP address and a port number, serving as an identifier.

A client-server architecture is typically adopted: the server waits for connection requests from clients by listening on a specific port; once a request is received, the server accepts the connection from the client socket to complete the connection process.

A server implementing a specific service listens on a well-known port. For example, an SSH server listens on port 22, an FTP server listens on port 21, and a web or HTTP server listens on port 80. All ports below 1024 are considered well-known and are used to implement standard services.

The principles of sockets will be explained below using Java, because compared with C/C++, Java provides an easier-to-use API and a richer library of network utility functions. Java provides 3 different types of sockets:

  • Connection-oriented (TCP) sockets are implemented through the Socket class.

  • Connectionless (UDP) sockets use the DatagramSocket class.

  • The MulticastSocket class is a subclass of the DatagramSocket class, and multicast sockets allow data to be sent to multiple recipients.

Although communication using sockets is widely used and efficient, it is considered a low-level means of communication among distributed processes. One reason is that sockets only allow the exchange of unstructured byte streams between communicating threads, and imposing structure on the data is the responsibility of the client or server application.

5.2 Remote Procedure Calls

One of the most common forms of remote service is the RPC paradigm, which was designed to abstract the mechanism of procedure calls between systems connected over a network. In many ways it is similar to the IPC mechanisms introduced earlier, and it is usually built on top of such systems. In this case, however, because we are dealing with an environment in which processes execute on different systems, a message-based communication scheme must be used to provide the remote service.

Unlike IPC messages, the messages exchanged in RPC communication are well structured and are therefore no longer merely data packets. Each message is sent to an RPC daemon listening on a port on the remote system, and each message contains an identifier specifying the function to be executed as well as the arguments passed to that function. The function is then executed as requested, and any output is returned to the requester in another message.

At this point a port is merely a number located at the beginning of a message packet. Typically a system has only one network address, but that address can contain multiple ports to distinguish among the many network services it supports. If a remote process needs a service, it sends a message to the corresponding port.

The semantics of RPC enable a client to invoke a procedure on a remote host as if it were calling a local procedure. The RPC system hides the details required to implement communication by providing a stub on the client side. Typically, each separate remote procedure has a corresponding stub. When a client calls a remote procedure, the RPC system invokes the corresponding stub and passes to it the arguments supplied to the remote procedure. This stub is responsible for locating the port on the server and marshaling the arguments. The stub then uses the message-passing mechanism to send a message to the server. A similar stub on the server side receives this message and executes the procedure on the server. If necessary, any return values are passed back to the client in the same manner.

Argument marshaling solves the problem of differences in data representation between client and server machines. Some systems store the most significant byte first (big-endian), whereas others store the least significant byte first (little-endian). Neither order is superior to the other; the choice is arbitrary in computer architecture. To resolve this difference, many RPC systems define a machine-independent data representation. One such representation is called external data representation (XDR). On the client side, argument marshaling involves converting machine-dependent data into XDR before sending it to the server. On the server side, the XDR data is unmarshaled and converted into the server-dependent representation.

Another key issue concerns the semantics of the call. A local procedure call fails only under extreme circumstances, whereas an RPC may fail, be duplicated, or be executed multiple times because of common network errors. One way to address this problem is to have the OS ensure that messages are executed exactly once rather than at most once.

  • At most once:

    • This can be achieved by attaching a timestamp to each message: the server must keep a record of the timestamps of all processed messages, or keep a sufficiently large history to ensure that duplicate messages can be detected.

    • Incoming messages whose timestamps are already in the history are ignored.

    • In this way, the client can send a message one or more times and ensure that it is executed only once.

  • Exactly once:

    • This requires eliminating the risk that the server may never receive the request.

    • To do this, the server must not only implement the "at most once" protocol described above, but must also acknowledge (ACK) to the client that the RPC call has been received and executed.

    • Such ACK messages are very common in network communication: the client must periodically resend each RPC call until it receives the corresponding ACK.

Another important issue concerns communication between the server and the client. In a standard procedure call, some form of binding occurs at link, load, or execution time, so that the name of the procedure call is replaced by the memory address of the procedure call. The RPC scheme likewise requires similar binding of client and server ports, but how does the client learn the port number on the server? Since the two do not share memory, neither has complete information about the other. There are two common solutions:

  • Binding information can be predetermined - in the form of a fixed port address.

    • At compile time, each RPC call has a fixed port number associated with it.

    • Once the program has been compiled, the server cannot change the port number of the requested service.

  • Binding can be done dynamically through a rendezvous mechanism.

    • Typically, the OS provides a rendezvous (also called a matchmaker) daemon on a fixed RPC port.

    • The client then sends a message to this rendezvous daemon containing the name of the RPC it needs to execute, asking for its port address.

    • After receiving the returned port number, all RPC calls are sent to that port until the process terminates (or the server crashes).

    • Although this approach requires the overhead of an additional initial request, it is more flexible than the first method.
