1 Overview

A thread is the basic unit of task scheduling and execution, including a thread ID, a program counter (PC), a register set, and stack space. A thread shares the code segment, data segment, and other OS resources of the process with other threads belonging to the same process. We can think of a thread as a lightweight process. The difference in address space is as follows:

A thread looks very much like a separate process, except for one difference: threads can share an address space and therefore can access the same data.

Like a process, a thread also has something called a thread control block (TCB), which is used to store the state, register values, stack information, and so on of each thread in the process. When a context switch occurs, the OS uses the TCB to save and restore context information.

1.1 Motivation

The reasons for using threads can be summarized in the following two points:

  • Parallelism: Transforming a single-threaded program into tasks that can execute the same job on multiple CPUs is called parallelization; and having each thread use one CPU is a natural and typical way to achieve parallelization.

  • Avoiding process blocking due to slow I/O: Threads allow I/O operations within a single program to overlap with other activities, similar to multiprogramming across processes.

Although these two points can also be achieved through multiple processes alone, what makes threads unique is that a shared address space makes it easy to share data, whereas processes are better suited for tasks that are logically relatively independent and do not need to share data much.

In addition to applications, the kernels of most OSes are also multithreaded. In Linux systems, the ps -ef command can be used to view the kernel processes currently running in the system, among which the thread kthreadd (pid = 2) is the parent thread of all threads.

Multithreading also has broader applications, including the implementation of various algorithms and data structures, as well as current CPU-intensive problems (data mining, graphics, AI, etc.).

1.2 Benefits

Responsiveness:

  • A multithreaded interactive application can keep running even when part of it is blocked or performing a long operation, thereby improving responsiveness to the user.

  • This characteristic is especially useful when designing user interfaces. If it is single-threaded, the application will be unresponsive until the operation is completed; whereas if it is executed in a separate asynchronous thread, the application can remain responsive to the user.

Resource sharing:

  • Processes can only share resources through techniques such as shared memory and message passing, and this must be arranged by the programmer.

  • By default, threads share the memory and resources of the process to which they belong, allowing an application to have several different active threads within the same address space.

Economy:

  • Allocating memory and resources when a process is created is not inexpensive; whereas threads share the resources of the process to which they belong, so the cost of creating and switching threads is lower.

  • Generally speaking, thread creation consumes less time and memory than process creation, and context switching between threads is usually faster than context switching between processes.

Scalability: Multithreading can unleash greater potential on multiprocessor architectures because threads can run in parallel on different processing cores.

2 Multicore Programming

On a single-core system, concurrency merely means that threads are interleaved in time, because the core can execute only one thread at a time.

But on a multi-core system, concurrency means that some threads can run in parallel, because the system can assign a thread to a separate core.

A concurrent system executes multiple tasks by making progress on all of them (not necessarily at the same time); a parallel system can execute multiple tasks at the same time. So even without parallelism, there can still be concurrency. Before the advent of multiprocessor and multi-core architectures, most computer systems had only one processor, so systems used the ability of the CPU scheduler to switch quickly between processes to provide the illusion of parallelism, but in reality such processes were running concurrently rather than in parallel.

2.1 Programming Challenges

Identifying tasks:

  • Specifically, this means examining the application to find tasks that can be divided into separate, concurrent tasks.

  • Ideally, these tasks are independent of one another, so they can run in parallel on different cores.

Balancing:

  • While identifying tasks that can run in parallel, the programmer must also ensure that these tasks have as equal an amount of execution workload as possible.

  • In some cases, a particular task may contribute less to the overall process than other tasks, and in such cases it may not be worthwhile to use a separate execution core to run that task.

Data splitting: Just as an application is divided into different tasks, the data accessed and operated on by these tasks must also be divided so that they can run on independent processor cores.

Data dependency:

  • It is necessary to check whether the data accessed by the tasks has dependencies between two or more tasks.

  • When one task depends on another task's data, the programmer must ensure that the tasks are executed synchronously to accommodate the data dependency.

Testing and debugging: When a program runs in parallel on multiple cores, many different execution paths may appear, so testing and debugging such concurrent programs is inherently more difficult than testing and debugging single-threaded applications.

2.2 Types of Parallelism

Data parallelism: Distribute subsets of the same data across multiple computing cores and perform the same operation on each core.

Task parallelism: Distribute tasks (threads) rather than data across multiple computing cores; each thread performs different operations, and they may process the same data or different data.

Why is it not better to have more threads?

  1. Switching overhead: The creation and switching of threads consume system resources; if too many threads are created, they will take up a large amount of system resources, causing the system load to become too high, and if a thread crashes, it may cause the process to crash.

  2. Synchronization issues: Too many threads may lead to

    • Race conditions: Multiple threads access and modify shared resources at the same time. Without appropriate synchronization mechanisms, this may lead to data inconsistency or incorrect results.

    • Deadlock: Multiple threads wait for each other to release resources, causing the program to be unable to continue executing.

3 Multithreading Model

Support for threads can be provided either by the user (i.e., user threads) or by the kernel (i.e., kernel threads).

  • User threads are supported above the kernel and do not require kernel involvement for management.

  • Kernel threads, on the other hand, are directly supported and managed by the OS, and almost all modern OSs support kernel threads.

It is not hard to imagine that some relationship must exist between user threads and kernel threads. Several common ways of establishing this relationship are discussed below.

3.1 Many-to-One Model

The many-to-one model maps multiple user threads to a single kernel thread.

Thread management is handled by a user-space thread library, so it is relatively efficient.

However, if a thread executes a blocking system call, the entire process will be blocked.

In addition, because only one thread can access the kernel at a time, multiple threads cannot run in parallel on a multicore system.

3.2 One-to-One Model

The one-to-one model maps a single user thread to a kernel thread.

Compared with the many-to-one model, it provides higher concurrency by allowing another thread to run when a thread makes a blocking system call.

At the same time, it also allows multiple threads to run in parallel on multiple processors.

The only drawback is that creating a user thread requires creating a corresponding kernel thread, and a large number of kernel threads may harm system performance.

Both Linux and Windows implement the one-to-one model.

3.3 Many-to-Many Model

The many-to-many model multiplexes multiple user threads onto a smaller or equal number of kernel threads.

The number of kernel threads depends on the specific application or the specific machine.

Impact on concurrency: Developers can create as many user threads as needed, and the corresponding kernel threads can run in parallel on multiple processors; in addition, when a thread executes a blocking system call, the kernel can schedule other threads to continue executing.

A variant of the many-to-many model (the two-level model): multiple user threads are still multiplexed onto a smaller or equal number of kernel threads, but at the same time a user thread is allowed to be bound to a single kernel thread.

Although this is the most flexible of the three models, it is difficult to implement in practice; in addition, as the number of processing cores on most systems continues to increase, limiting the number of kernel threads has become less important, so most operating systems today still adopt the one-to-one model.

4 Thread Libraries

Thread libraries provide programmers with an API for creating and managing threads. The methods for implementing thread libraries include:

  • Providing the library entirely in user space, without kernel support: All the code and data structures of the library exist in user space, which means that calling functions in the library results in local function calls in user space rather than system calls.

  • Implementing a kernel-level thread library directly supported by the OS: The library's code and data structures reside in kernel space, and calling functions in the API typically triggers system calls to the kernel.

Several commonly used thread libraries:

  • POSIX Pthreads: As a thread extension of the POSIX standard, it can be provided either as a user-level library or exist as a kernel-level library.

  • Windows thread library: A kernel-level library for Windows systems.

  • Java thread API: Allows threads to be created and managed directly in Java programs. However, since the JVM in most cases runs on top of a host OS, the Java thread API typically makes use of existing thread libraries on the host system for implementation.

Windows systems -> Windows API

UNIX, Linux, macOS -> Pthreads

For the POSIX and Windows thread models, any global data is shared by all threads belonging to the same process. However, since Java does not have the concept of "global data," accessing shared data between threads must be explicitly arranged.

Strategies for creating multithreading are divided into synchronous threading and asynchronous threading:

  • Asynchronous threading: After the parent thread creates a child thread, the parent thread can still continue executing its current task, so the parent and child threads can run concurrently and independently. Since these threads are independent of one another, they usually share little data. This approach is commonly used in designing web servers, responsive user interfaces, and so on.

  • Synchronous threading: After the parent thread creates one or more child threads, these child threads can execute tasks concurrently, but the parent thread must wait for all child threads to terminate before it can continue executing. When each child thread completes its work, it terminates and joins with the parent thread; only after all child threads have joined can the parent thread resume execution. Generally speaking, synchronous threading involves extensive sharing of data among threads, for example, the parent thread may consolidate the computation results of the various child threads.

Pthreads refers to the POSIX standard that defines an API for thread creation and synchronization. This is a specification for thread behavior, not an implementation. Therefore, OS designers can implement this specification in any way they wish, and many OSs have implemented this specification.

5 Implicit Threading

With the advancement of multi-core processing technology, the number of processes contained in an application will also increase accordingly. Designing such a program is by no means a simple task: programmers must not only deal with the challenges listed earlier, but also other challenges such as program correctness.

One way to address these difficulties and better support concurrent and parallel application design is to shift the creation and management of threads from application developers to compilers and runtime libraries. This strategy is called implicit threading. Several different design approaches will be discussed below that enable applications to take full advantage of multi-core processors through implicit threading.

It should be noted that these strategies usually require application developers to identify tasks that can run in parallel, rather than the threads themselves. Tasks are usually written as functions, which are then mapped by the runtime library onto separate threads, and a many-to-many model is generally adopted. The advantage of this approach is that developers only need to determine the specific content of the parallel tasks, while the specific details of thread creation and management are handled by the relevant libraries.

5.1 Thread Pools

Previously, we introduced a multithreaded web server: whenever the server receives a request, it creates a separate thread to handle that request. However, such a multithreaded server still has some problems:

  • Consider the time cost required to create a thread, and the fact that once the task is completed, the thread is discarded

  • If every concurrent request is allowed to be served by a newly created thread, then the number of simultaneously active threads in the system will be unlimited, and unlimited threads may exhaust system resources

One solution to these problems is to use thread pool technology. Its basic idea is:

  • Create a certain number of threads at startup and place them in a pool; these threads remain idle and wait to be assigned tasks

  • When the server receives a request, it does not directly create a new thread, but instead submits the request to the thread pool and then continues waiting for other requests

  • If there is an idle thread in the pool, that thread will be awakened and immediately handle the request; if no thread is available, the task will queue and wait until a thread is released

  • Once a thread completes its work, it returns to the pool and waits for the next work assignment

  • Thread pools work best when the tasks submitted to the pool can be executed asynchronously

The benefits of using a thread pool include:

  • Handling requests with ready-made threads is usually faster than waiting to create a new thread

  • A thread pool limits the number of threads that exist at any moment, which is especially important for systems that cannot support a large number of concurrent threads

  • Separating the tasks to be executed from the mechanism that creates tasks allows us to use different strategies to run tasks, such as scheduling tasks to execute after a delay or periodically

The number of threads in a thread pool can be set heuristically based on factors such as the number of system CPU cores, the amount of physical memory, and the expected number of concurrent client requests. More advanced thread pool architectures can dynamically adjust the number of threads in the pool according to usage patterns; their additional advantage is that when system load is low, they can maintain a smaller thread pool size, thereby reducing memory usage.

5.2 Fork Join

The thread creation strategy introduced in the "Thread Libraries" section is commonly referred to as the fork-join model.

The parent thread creates (forks) one or more child threads, and then waits for these child threads to terminate and joins with them (retrieving and integrating the results of the child threads).

This synchronization model is usually a form of explicit thread creation, but it is also very suitable for implicit threading; for the latter, the fork phase does not directly construct threads, but instead specifies parallel tasks.

Typically, a library is used to manage the number of threads created and to handle the assignment of tasks to each thread, such as the related APIs provided by Java, etc.
