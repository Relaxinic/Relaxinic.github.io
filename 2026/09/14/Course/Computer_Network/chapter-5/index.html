1 Overview

1.1 Network Communication Between Processes

The entities that actually communicate in a computer network are processes running on the hosts at the two ends. The transport layer's main task is to provide direct logical communication services between application processes on different hosts. Transport-layer protocols are therefore also called end-to-end protocols.

1.2 Two Important Protocols

Transmission Control Protocol (TCP) provides connection-oriented, reliable data transfer to the upper layer. The communicating parties first establish a logical TCP connection, rather than a physical connection, and release it after transmission. Reliability requires connection management, acknowledgments, timeout retransmission, flow control, congestion control, and other mechanisms. TCP is complex, has a relatively large segment header, and consumes more processor resources.

User Datagram Protocol (UDP) provides connectionless, unreliable data transfer. The parties do not establish a connection before sending data, and UDP does not implement the mechanisms needed for reliable transmission. Its implementation is simple and its datagram header is small.

1.3 Transport-Layer Port Numbers

The TCP/IP transport layer uses port numbers to identify different application processes. A port number is 16 bits long and ranges from 0 to 65535.

Common well-known ports to remember:

  • FTP: 21/20.

  • SMTP: 25.

  • DNS: 53.

  • DHCP: 67/68.

  • HTTP: 80.

  • BGP: 179.

  • HTTPS: 443.

  • RIP: 520.

Port numbers have only local significance: they identify application processes within one computer's protocol stack. Identical port numbers on different computers are independent. TCP and UDP port-number spaces are also independent of each other.

1.4 Sender Multiplexing and Receiver Demultiplexing

Multiplexing at the sender and demultiplexing at the receiver are implemented through sockets, which form the interface between the application and transport layers and the API between applications and the network.

A UDP socket is identified by an IP-address/port-number pair. On receiving a UDP datagram, the transport layer checks its destination port and delivers it to the corresponding socket. Datagrams with the same destination IP address and destination port are delivered to the same socket regardless of their source IP addresses and ports. The receiving process uses the source address and port to send a response.

The UDP socket communication procedure is:

  • socket(): create a socket.

  • bind(): bind an address and port.

  • recvfrom(): receive a request.

  • sendto(): send a response.

  • close(): close the socket.

To serve many clients simultaneously, a TCP server uses a listening socket and connected sockets. The listening socket waits for connection requests on a well-known port. After receiving a request, the server creates a connected socket and can create a new process to serve that client. Each connected socket communicates with only one client.

A TCP connection is identified by the four-tuple of source IP address, destination IP address, source port, and destination port. For incoming segments, the source address and port belong to the client, while the destination address belongs to the server and the destination port is the server's listening port. The server uses the four-tuple to deliver each segment to the correct connected socket.

The TCP socket communication procedure is:

  • socket(): create a socket.

  • bind(): bind an address and port.

  • listen(): begin listening and set the queue size; this call is nonblocking.

  • accept(): take an established connection from the connected queue and create a new socket for it. If the queue is empty, block the caller until a new connection arrives.

  • Communicate with the client using the returned socket.

3 Transmission Control Protocol

3.1 Segment Header Format

Sequence number: 32 bits, ranging from 000 to 232−12^{32} - 1232−1 and wrapping back to 0 after the last value. It identifies the first byte of the segment's data payload.

Acknowledgment number: 32 bits with the same range and wraparound. It identifies the first byte of data expected in the next segment from the other party and cumulatively acknowledges all preceding data.

ACK flag: the acknowledgment field is valid only when ACK=1\mathrm{ACK} = 1ACK=1. TCP requires all segments sent after connection establishment to have ACK set to 1.

The sequence number, acknowledgment number, and ACK flag are fields used to implement reliable transmission.

Data offset: 4 bits, measured in 4-byte units. It gives the distance from the beginning of the segment to the beginning of the payload, thereby indicating the header length.

Reserved: 6 bits reserved for future use and set to 0 in this header format.

Window: 16 bits, measured in bytes. It indicates the sender of this segment's receive-window size, namely the available receive-buffer space. Using the receiver's capacity to limit how much data the sender transmits is called flow control.

Checksum: 16 bits, used to detect transmission errors in the entire TCP segment.

The sender calculates the checksum as follows:

  • Set the TCP checksum field to 0.

  • Divide the pseudoheader, TCP header, and payload into 2-byte words. If their combined length is odd, append one all-zero byte.

  • Add all words using one's-complement arithmetic, then complement the sum. Any carry beyond the word size must be added back into the sum.

  • Write the resulting value into the TCP checksum field.

The receiver checks the segment by prepending a 12-byte pseudoheader, dividing the pseudoheader, header, and payload into 2-byte words, summing them with one's-complement arithmetic, and complementing the result. A result of 0 indicates that no error has been detected; a nonzero result indicates an error.

SYN flag: used in the three-way handshake to establish a connection. SYN=1, ACK=0\mathrm{SYN} = 1,\ \mathrm{ACK} = 0SYN=1, ACK=0 identifies a connection request. A response accepting the connection has SYN=1, ACK=1\mathrm{SYN} = 1,\ \mathrm{ACK} = 1SYN=1, ACK=1. Thus a segment with SYN set is either a connection request or a connection response.

FIN flag: used in the four-message connection-release procedure. FIN=1\mathrm{FIN} = 1FIN=1 means that the sender has finished sending data and requests connection release.

RST flag: resets a TCP connection. A value of 1 indicates a serious connection error requiring release and reestablishment. It is also used to reject an invalid segment or refuse a connection.

PSH flag: the sender sets PSH and immediately constructs and sends a segment instead of accumulating more data. The receiver delivers its data to the application promptly rather than waiting for more data. For efficiency, TCP may otherwise delay sending or delivering data to process more at once. During interactive communication, an application may request PUSH so that a command can receive an immediate response.

URG flag: the urgent-pointer field is valid when URG=1\mathrm{URG} = 1URG=1 and invalid when URG=0\mathrm{URG} = 0URG=0.

Urgent pointer: 16 bits, measured in bytes, indicating the urgent data's extent. A sender can place urgent data at the front of its send buffer and immediately send it in a segment. The pointer identifies how much urgent data precedes the ordinary data. The receiver extracts urgent data from a segment with URG set and delivers it directly to the application rather than leaving it queued in the receive buffer.

Options have variable length, up to 40 bytes. They include:

  • Maximum segment size (MSS): the maximum payload length, not the length of the whole TCP segment.

  • Window scale: expands the window to improve throughput.

  • Timestamps: measure round-trip time (RTT) and help handle sequence-number wraparound through protection against wrapped sequence numbers (PAWS).

  • Selective acknowledgment: supports selective acknowledgment of received data.

Padding: if the options plus the 20-byte fixed header do not make a multiple of 4 bytes, zero bits are added so that the header length is divisible by 4, as with IPv4 header padding.

3.2 Transport Connection Management

A TCP connection has three phases: establishment through a three-way handshake, reliable data transfer over the established connection, and release through a four-message exchange after transfer is complete.

Establishing a TCP Connection

The three-way handshake addresses three main requirements:

  • Each side confirms the other's existence.

  • The sides negotiate parameters such as maximum segment size, maximum window size, and timestamp options.

  • The sides allocate and initialize transport-entity resources, including buffers, state variables, and connection-table entries.

A transmission control block (TCB) includes the TCP connection table, pointers to send and receive buffers and the retransmission queue, and current send and receive sequence numbers.

The client's connection-request segment has SYN set to 1 and an initial sequence number xxx. In the handshake described here, a SYN segment carries no data but consumes one sequence number. Thus the client's first data byte will have sequence number x+1x + 1x+1.

The server's connection-request acknowledgment also has SYN set to 1. It chooses initial sequence number yyy and sets the acknowledgment number to x+1x + 1x+1, acknowledging the client's initial sequence number.

The client's next segment has sequence number x+1x + 1x+1 and acknowledgment number y+1y + 1y+1. An ordinary acknowledgment may carry data; if it does not, it consumes no sequence number, so the next data segment still begins at x+1x + 1x+1.

Three messages rather than two prevent an obsolete connection request that arrives unexpectedly at the server from incorrectly establishing a connection.

Releasing a TCP Connection

The four-message release procedure is illustrated below.

The client's release segment sets both FIN and ACK to 1, requesting release while acknowledging previously received data. Its sequence number is uuu, one more than the last data-byte sequence number it has sent, and its acknowledgment number is vvv, one more than the last data-byte sequence number it has received. A FIN segment consumes one sequence number even without data.

The server acknowledges with sequence number vvv and acknowledgment number u+1u + 1u+1. It enters CLOSE-WAIT, and the connection is half-closed: the client-to-server direction is closed, but the server may still send data and the client must continue receiving it. This state may last for some time.

When the server finishes, it sends its own FIN with sequence number www, which may exceed vvv because additional data may have been sent during the half-close, and acknowledgment number u+1u + 1u+1. The client returns an acknowledgment with sequence number u+1u + 1u+1 and acknowledgment number w+1w + 1w+1.

The maximum segment lifetime (MSL) is suggested as 2 minutes in the described procedure. The client remains in TIME-WAIT for 2MSL2\mathrm{MSL}2MSL, or 4 minutes, before entering CLOSED. This is an engineering choice, and implementations may use a smaller MSL appropriate to their networks.

Waiting for 2MSL2\mathrm{MSL}2MSL allows the server to receive the final acknowledgment and close. It also allows all segments from the old connection to disappear, preventing them from appearing in a subsequent connection.

3.3 Flow Control

TCP provides flow control to prevent a sender from transmitting so quickly that the receiver cannot keep up and its receive buffer overflows.

Example.

To break a deadlock caused by the loss of a nonzero-window advertisement, TCP maintains a persist timer for each connection. Receiving a zero-window advertisement starts the timer. When it expires, the sender transmits a zero-window probe carrying one byte of data. The receiver acknowledges it with its current receive-window value. If the window remains zero, the timer is restarted; if it is nonzero, normal transmission can resume.

Even with a zero receive window, the protocol described here accepts zero-window probes, acknowledgments, and segments carrying urgent data. Probes also have a retransmission timer, so a lost probe can be retransmitted and does not cause permanent deadlock.

3.4 Congestion Control

Congestion occurs when demand for a network resource exceeds its available capacity for some period, degrading network performance. Without control, overall throughput can decrease as the offered load increases.

  • Flow control limits a particular sender according to its receiver's capacity and concerns that pair's traffic.

  • Congestion control lets a source adjust its sending rate according to multiple network factors and a congestion-control algorithm. It is a global issue involving hosts, routers, and other network resources.

The following discussion assumes:

  • Data flows in one direction and acknowledgments in the other.

  • The receiver always has enough buffer space, so the sender's window is determined only by congestion; receiver flow control is ignored.

  • Window sizes are discussed in units of maximum segment size (MSS), rather than bytes, even though TCP is byte-stream oriented.

Slow Start and Congestion Avoidance

Slow start means that few segments are initially injected into the network; it does not mean that the congestion window grows slowly. Congestion avoidance means increasing the congestion window linearly to make congestion less likely, rather than completely preventing congestion.

Fast Retransmit and Fast Recovery

Fast retransmit retransmits a missing segment as soon as possible instead of waiting for the retransmission timer. The receiver immediately sends acknowledgments, including duplicate acknowledgments for out-of-order arrivals, rather than waiting to piggyback them on outgoing data. Upon three consecutive duplicate acknowledgments, the sender immediately retransmits the corresponding segment.

For an isolated lost segment, this avoids timeout retransmission and prevents the sender from unnecessarily treating it as severe congestion and reducing cwnd to 1. In practice, fast retransmit can improve overall network throughput by roughly 20%.

In fast recovery, the sender sets both ssthresh and cwnd to half the current cwnd and begins congestion avoidance. Some implementations initially set cwnd=new ssthresh+3\mathrm{cwnd} = \text{new ssthresh} + 3cwnd=new ssthresh+3. Three duplicate acknowledgments indicate that three segments have left the network and are buffered at the receiver, so they no longer consume network resources and the congestion window may temporarily be increased by three.

For TCP throughput, ignore the short slow-start phase and consider only congestion avoidance. Let WWW be the congestion window at packet loss. The throughput is then W/RTTW/\mathrm{RTT}W/RTT. After reducing the window to W/2W/2W/2, it is W/(2RTT)W/(2\mathrm{RTT})W/(2RTT). If RTT and WWW remain approximately constant throughout the connection, the average throughput is

Average throughput=0.75WRTT.\text{Average throughput} = \frac{0.75W}{\mathrm{RTT}}.Average throughput=RTT0.75W​.

3.5 Choosing the Retransmission Timeout

A timeout that is too short causes unnecessary retransmissions, while one that is too long delays recovery from packet loss. Intuitively, it should exceed RTT, but RTT varies. The Jacobson algorithm estimates it as follows.

The smoothed RTT is an exponentially weighted average:

RTTS1=RTT1,New RTTS=(1−α) Old RTTS+α New RTT sample.\begin{aligned} \mathrm{RTT}_{S1} &= \mathrm{RTT}_1, \\ \text{New }\mathrm{RTT}_S &= (1 - \alpha)\,\text{Old }\mathrm{RTT}_S + \alpha\,\text{New RTT sample}. \end{aligned}RTTS1​New RTTS​​=RTT1​,=(1−α)Old RTTS​+αNew RTT sample.​

Here 0≤α<10 \le \alpha < 10≤α<1. A value close to 0 gives new samples little influence; a value close to 1 gives them greater influence. RFC 6298 recommends α=1/8\alpha = 1/8α=1/8.

The smoothed RTT deviation is

RTTD1=RTT1/2,New RTTD=(1−β) Old RTTD+β∣RTTS−New RTT sample∣.\begin{aligned} \mathrm{RTT}_{D1} &= \mathrm{RTT}_1/2, \\ \text{New }\mathrm{RTT}_D &= (1 - \beta)\,\text{Old }\mathrm{RTT}_D + \beta\left|\mathrm{RTT}_S - \text{New RTT sample}\right|. \end{aligned}RTTD1​New RTTD​​=RTT1​/2,=(1−β)Old RTTD​+β∣RTTS​−New RTT sample∣.​

Here 0≤β<10 \le \beta < 10≤β<1, and RFC 6298 recommends β=1/4\beta = 1/4β=1/4.

Textbooks may interchange the meanings of α\alphaα and 1−α1 - \alpha1−α, and similarly for β\betaβ. A large coefficient, such as 0.9 or 0.875, usually weights the old estimate; a small coefficient usually weights the new sample. Check which formula is being used.

RTO should be slightly greater than the smoothed RTT, rather than any individual sample. RFC 6298 gives

RTO=RTTS+4RTTD.\mathrm{RTO} = \mathrm{RTT}_S + 4\mathrm{RTT}_D.RTO=RTTS​+4RTTD​.

Karn's Algorithm

After a retransmission, an acknowledgment does not reveal whether it acknowledges the original segment or the retransmission. RTT therefore cannot be measured accurately from that acknowledgment, and using it would give an incorrect RTO.

Karn's algorithm excludes RTT samples from retransmitted segments when calculating the smoothed RTT. Retransmission therefore does not produce a new RTT estimate or a new RTO through the estimation formula.

This introduces another problem: if delay suddenly increases and remains high, perhaps after a topology change, the old RTO expires repeatedly. Since retransmitted segments supply no RTT samples, the estimate cannot adapt. The correction is to increase RTO after each retransmission, typically doubling it.
